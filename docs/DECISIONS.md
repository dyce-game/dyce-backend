# Decisions (ADRs): backend

One entry per decision, newest first. App-side decisions (ADR-001 stack, 002 avatar system, 003 domain, 006 hoisted node_modules for Metro) are in `Dyce/docs/DECISIONS.md`.

## ADR-015 · Profile and Settings · 2026-11-15
Context: SPEC §12 lists Settings (account, privacy, notifications, blocked, Pool limits, data, help and legal) and §10 the profile. Most of those controls need features that don't exist yet; one real privacy control does: `profiles.request_policy` (`everyone | fof | nobody`) is already enforced by friend requests and first messages.
Decision:
- **`PATCH /profile`** changes `displayName` (1-40 characters) and/or `requestPolicy` and returns the updated `/me`. The schema is strict, so the username can't be sent: **changing a username is deliberately not built**, because the design promises a 30-day cooldown and a 14-day reservation of the old name that the SPEC doesn't define (BACKLOG). `GET /me` now includes `profile.requestPolicy`.
- **Only controls that do something are shown.** Settings has "Who can add and message me" (Everyone / Friends of friends / Nobody, saved immediately, and checked end to end: with Nobody a stranger's friend request is refused with `requests_closed`), your account details, Blocked people, a read-only Theme row ("Follows your phone": no in-app theme toggle, CLAUDE.md) and Log out. Not shown until their feature exists: notification switches (push), "who can see me online" and Show me in Space (presence, Space search), Pool limits and Free-only (Pools), Download my data and Delete account (data export and deletion jobs: NDPA work, BACKLOG), Help and legal (legal copy).
- **Profile** shows avatar (with an edit button to the starter-look picker), name, @username, level and XP, a Friends card (count and waiting requests), Edit profile and Settings. The design's stat cards, badges, Notifications card, Share and Lagos location wait for games, badges, push, invite links and city opt-in. The XP bar waits for a level curve the docs don't define.
- **Entry point:** the header avatar on every tab opens Profile; Friends, Edit profile, Settings and Blocked people are reached from there.
- **Log out** tells the server to end the session (best effort, so it works offline), clears cached data and leaves for Welcome.
Consequences: no migration. Owner: social-discovery-engineer

## ADR-014 · Avatars, phase A: starter looks · 2026-11-15
Context: AVATAR_GUIDEBOOK §8 phase A ships the 220 generated profiles as the player's look until the editable 3D rig exists (phase B). The backend is NestJS + PostgreSQL with no Supabase Storage, and nothing renders avatars server-side yet.
Decision:
- **Stored as `{ v: 1, preset: 'dyce_av_042' }` in `profiles.avatar`** (the column already existed as `'{}'`, meaning none). `@dyce/shared` has `avatarConfigSchema` (strict, preset must be 001-220), `parseAvatar` (anything invalid reads as "no avatar" so one bad row never breaks a list) and `setAvatarSchema`. The `v: 2` rig schema waits for the artist's part manifest (it needs real part ids and morph names) and is added in phase B, which migrates v1 presets to the matching v2 look.
- **API:** `PUT /profile/avatar` saves the look, counts as the onboarding "avatar" step and can be repeated to change it. `GET /me` returns `profile.avatar`. Every person the app shows carries `avatar` (`PublicUser`, friends, friend requests, blocked people, money parties): the look is public to anyone who can see the person, like the name. No new migration.
- **Images ship inside the app**, not from a CDN: `tools/avatar/make_starter_looks.py` cuts 256px WebP thumbnails (about 2 MB for all 220) and generates `starter-looks.ts` (skin tone, hair type, a spoken description) and the static `require` table Metro needs. The 1024px originals stay in `assets/avatar-profiles/` for marketing and the future renderer. Works offline and needs no image hosting; the cost is app size and that a new look needs a new release. Phase B's server-rendered, hash-named images (`<hash>@<size>.webp`) replace this behind the same `<UserAvatar>`.
- **UI:** `<Avatar>` in `@dyce/ui` is presentational (a picture, or the person's initial); the app's `<UserAvatar avatar name size>` maps a saved look to its picture. The "Pick your look" screen (onboarding, or `/avatar` later from Edit profile) has a large preview, skin-tone and hair-type filters, the grid, a shuffle button, Save, and Skip in onboarding.
- **Not built (deferred to phase B or later):** the render service skeleton and `tools/avatar/{export,build,viewer}` (they need the artist's rig; there is nothing to render yet), `expo-image` caching (not installed; plain `Image` is enough for bundled files and arrives with remote images), a 200-row list performance test on a device, and "Make from a selfie".
Consequences: every list that shows a person shows their face. People who skip see their initial. Owner: avatar-engineer

## ADR-013 · Block and report · 2026-11-15
Context: SPEC §11 needs blocking (they can't message, invite or see you online) and reporting (reasons plus optional evidence from chat). The data model had `blocks` and `reports` tables and every list, send and lookup already treated a blocked pair as strangers; nothing could create or remove a block or file a report.
Decision:
- **Endpoints:** `GET /blocks`, `POST /blocks`, `DELETE /blocks/:userId`, `POST /reports`. `SafetyService` is a plain class like the others.
- **Blocking is silent and ends the friendship.** The blocked person is told nothing; to them the blocker looks like a user who doesn't exist (existing behaviour in messaging, friends, wallet). The blocker is told "you blocked them" if they try to write. Blocking deletes any friendship or pending request between the two, because that is what people mean by it; unblocking does **not** restore it. The conversation and its history are kept (hidden, not deleted), so it reappears if both become friends again. Idempotent and race-safe (pair lock).
- **Reports** have a fixed set of reasons (`cheat, abuse, scam, spam, name, other`, enforced by a CHECK), an optional note (≤500), optional `conversationId` (must be the reporter's own direct chat with the reported person) and `messageId` (must be in it), and `alsoBlock`. When a conversation is attached the **latest 20 messages are copied into `reports.evidence`** so a moderator sees what the reporter saw even if messages are deleted later. The same reporter, person and reason within 24 hours is one report (double taps and retries); 20 reports per Lagos day (`reports_per_day`). The reported person is never told, and has no way to see that a report exists. A report is kept even if the person is later disabled or blocks the reporter.
- **Not built:** the moderation queue UI and any action on a report (status stays `open`), outcome notifications to the reporter, holding or refunding a Pool stake on a report, and attaching game moves as evidence (there are no matches yet). The app's "A person reviews it" copy promises no deadline.
Consequences: migration 0011. Messaging's "request" banner and Chat info both offer Report and Block. `@dyce/shared` gains `REPORT_REASONS`, `reportSchema`, `blockSchema`. Owner: trust-safety-compliance

## ADR-012 · Wallet API, money cards and request codes · 2026-11-15
Context: the ledger and its SQL functions existed (ADR-004); Phase 1 needs them reachable from the app: balance, send, request with a QR code, pay a scanned code, history and receipts, with cards in chats.
Decision:
- **Layering.** `WalletService` (a plain class) sits over `LedgerRepo`. Limits, balances, blocks, expiry and idempotency stay in PostgreSQL; the service adds who may pay whom, shapes responses and posts chat cards. Endpoints under `/wallet`: `GET /wallet`, `POST /wallet/topup`, `POST /wallet/send`, `GET /wallet/history`, `GET /wallet/transactions/:id`, `GET|POST /wallet/requests`, `GET /wallet/requests/:code`, `POST .../pay`, `POST .../cancel`.
- **Idempotency keys are scoped to the caller** (`send:<user>:<key>`, `pay:<user>:<key>`). The ledger's key is globally unique, so an unscoped key would let one user replay another's key and read back their transaction id. The app makes one key per confirmation and reuses it on retry.
- **Who can be sent money:** friends, contacts, or someone whose chat both sides have accepted (spec §3). Strangers are paid only by scanning their request code (§4), because the requester shared it on purpose; the resulting chat lands in the requester's Requests, not their Chat.
- **Chat cards.** Message kinds `money_sent` and `money_request` carry a JSON `payload` (amount, note, txn id; or code, status, expiry) and a text `body` ("Sent ₦5,000", "Paid ₦2,000 · suya") so previews and old clients still read sensibly. The card's message id **is** the transaction id (or request id), so posting is idempotent (`ON CONFLICT DO NOTHING`) and a retry re-posts a card lost after the money moved. A card failing never fails the payment (logged). When a request is paid or cancelled, the card's `status` is updated and re-sent live; the app replaces a request card with its newer copy. Cards bypass the stranger message limits: the money movement already passed its own checks.
- **Request codes.** The QR holds only `https://dyce.games/r/<code>`. The Pay sheet always reads the requester, amount and note from `GET /wallet/requests/:code`, never from the QR. An open request past its time reads as `expired` immediately, whether or not a job has marked it. Someone who blocked you (or whom you blocked) makes a code look missing. QR requests last 15 minutes, requests sent to a friend 7 days, at most 10 open at a time.
- **History** is read from the ledger entries of the caller's wallet account, newest first, paged by `(created_at, id)` with a microsecond cursor (the ledger's timestamps are not millisecond-rounded). Receipts only open for someone whose wallet the transaction touched.
**Update (design pass, 2026-11-15):** the History chips follow the design (`all | pool | transfer | bonus` replace the earlier `sent | received | requests | topups | games`); `GET /wallet` also returns `stats` (won this week, win rate, current streak) and `locked` (stakes held in unfinished Pools), all zero until games are played; `GET /wallet/weekly` returns the last 7 Lagos days of net movement and top-ups (the History bars and the Top-up week grid; the welcome gift is not "net").
Not done in this step (see BACKLOG): biometric / PIN confirmation, a per-day cap on resolving codes that belong to strangers (only a per-IP throttle for now), the personal "My code" QR and paying a personal code, a scheduled job that marks expired requests and their cards, push for money, disputes, and Pool UI.
Consequences: `@dyce/shared` gains the wallet schemas and the `Message` type is now a union (`text | money_sent | money_request`), which the app consumes. Owner: wallet-payments-engineer

## ADR-011 · Two repositories: the Expo app (Dyce) and the backend (dyce-backend) · 2026-11-15
Context: the app and the server have different toolchains (Metro and EAS vs Node, NestJS and PostgreSQL), different owners, release rhythms and CI, and the single monorepo made each carry the other's tooling. They still must agree on API contracts, money utilities and the game rules engines (CLAUDE.md: the same engine code runs in the app and on the server).
Decision:
- **dyce-backend** is a pnpm workspace with `apps/api` (NestJS, SQL migrations, DB tests), `packages/shared` (zod schemas, money, formatting, phone and username rules, query keys, config) and `packages/games` (rules engines), and later `apps/game-server` (Colyseus). It owns the contracts: the API and the schemas change together, in one commit.
- **Dyce** is the Expo app, now at the repo root (no `apps/mobile`), plus `packages/ui` (design tokens and primitives, which only the app uses). It depends on `@dyce/shared` and `@dyce/games` through `link:../dyce-backend/packages/*`, consumed as TypeScript source (the `dyce-source` export condition), so there is one copy and nothing to publish. Metro watches the linked folder and resolves packages from the app's own `node_modules` (so `zod` is a single copy); Jest maps the two packages to source.
- **Docs follow ownership.** Product docs (SPEC, DESIGN_SYSTEM, GAMES, AVATAR_GUIDEBOOK), BUILD_PLAN, STATUS, `design/`, `assets/` and the app ADRs (001-003, 006) stay in Dyce; ARCHITECTURE, WALLET_AND_QR, the backend ADRs (004, 005, 007-010, this one), TEST_PLAN for the server, and the server's CI live here. History before the split stays in Dyce; this repo starts from the split commit.
Consequences: the two folders must be checked out side by side (the app's CI checks out both). A contract change is a backend commit first, then an app commit that uses it; the app always sees the backend's working tree, so a release build of the app must pin the backend commit it was built against. The backend's own tests no longer exercise the app's use of the contracts, so the app keeps its own tests for that. Owner: platform-architect

## ADR-010 · One-to-one messaging, Requests and live delivery · 2026-11-15
Context: Chat must feel instant, keep strangers out of Chat (CLAUDE.md), and not leak who has opened what. This slice is 1:1 text chat; groups, bots, voice, photos, reactions, deletes, game and money cards are later work.
Decision:
- **Model.** One `direct` conversation per pair (`conversations.direct_key` = "low:high", unique), two `conversation_members` rows. A conversation is created by opening it (sends nothing) and appears in lists only once it has a message. Member states: `active`, `request`, `declined`.
- **Requests.** A message to a non-friend creates the conversation with the *recipient* in `request`: it never shows in their Chat or Chat badge. Before they answer, the sender may send `request_messages_before_accept` (3) messages. The first message is also subject to the recipient's `request_policy` (`nobody`, `fof`) and to `stranger_requests_per_day` (20 new people per Lagos day). Replying, or tapping Accept, makes it active. Decline is **silent**: the member becomes `declined`, the sender sees nothing change and can keep writing up to the same cap, but the recipient gets no live events. While a conversation is a request, opening it sends **no read receipt** (the sender's `peerReadAt` stays null).
- **Friends override.** Once two people are friends, a request or ignored conversation counts as active for both. This is decided when reading (a `CASE` on the friendship row), so nothing needs rewriting when a friend request is accepted.
- **Sending.** The app picks the message id (a UUID), so retrying is safe: the same id returns the stored message and sends nothing; the same id in someone else's conversation is `message_id_taken`. Bodies are trimmed, 1-4000 characters (also a DB CHECK). Created times are server time; history is paged newest-first by the cursor `(created_at, id)`. Sending does **not** mark the thread read (that would hide unread messages the sender hasn't seen).
- **Read state.** `last_read_at` per member, only moves forward. Unread = the other person's messages after it (capped at 99). The Chat tab badge counts unread in active chats, not requests.
- **Realtime.** The `ws` library on the same HTTP server and port, at `/realtime` (no Nest gateway decorators, so it is unit-testable). The first frame is `{type:'auth', token}` (tokens are never in URLs or logs); the socket closes with 4403 when that token expires and the app reconnects with a fresh one, so a revoked session loses live delivery within one access-token lifetime. Limits: 5 sockets per user (oldest dropped), 4 KB frames, 5 s to authenticate, typing 20 per 10 s per socket. Events: `message` (sent to both people, so the sender's other devices update), `read`, `typing`. Typing is checked against the database per signal (member, not blocked, not ignored). Live delivery is best effort: the HTTP API is the source of truth, and on every (re)connect the app refetches its lists and open threads.
- **Single instance.** The hub is in-process. Running more than one API instance needs a shared bus (Redis pub/sub) behind `RealtimeHub.publish` first; until then a message sent through instance A won't reach sockets held by instance B.
- **App.** TanStack Query holds threads (infinite query, newest first) and live events patch that cache. A Zustand **outbox** holds messages being sent or failed (Retry / Delete, with the reason) so they survive navigating away. Typing is a small Zustand store that expires by itself. The thread is an inverted `FlatList` (FlashList later, with the 5,000-message performance pass). On web Enter sends and Shift+Enter is a new line; on phones Return is a new line and the button sends.
- **Deliberately not in this slice** (see BACKLOG): Groups and Bots filters, the "Live now" strip, online dots and "Active now", the "Add friend" choice when accepting a request, a read-receipt opt-out, mute/archive/delete swipes, replies, reactions, delete for me/everyone, voice notes, photos, the Games and money buttons in the composer, and push for new messages. The design's unread count beside the back arrow is omitted.
Consequences: `ws` is a direct dependency of `apps/api`. `TokenService.verifyAccessWithExpiry` exposes token expiry. Block and report (trust-safety) reuse `blocks`, which messaging already honours (blocked people disappear from lists and look nonexistent). Owner: messaging-engineer

## ADR-009 · Friends list, accept and ignore · 2026-11-15
Context: friend requests existed (ADR-008) but nobody could see, accept or decline them. SPEC says anything from a non-friend goes to Requests, and declining must not become a way to harass or to learn who ignored you.
Decision:
- **Endpoints:** `GET /friends` (A-Z), `GET /friends/requests` (`incoming` and `outgoing`, with mutual-friend counts), `POST /friends/requests/:userId/accept`, `POST /friends/requests/:userId/decline`, `DELETE /friends/requests/:userId` (cancel your own), `DELETE /friends/:userId` (remove). All idempotent; each pair is serialised with an advisory lock.
- **Declined is a real state** (`friendship_status` gains `declined`, plus `responded_at`), not a deleted row. The row is what stops the same person re-sending and re-notifying you.
- **Silent ignore.** The sender is never told. After you decline, their screen still says "Requested" (`pending_out`), they cannot re-send past it, and the daily request cap still applies.
- **Adding back accepts.** If you later add someone whose request you declined, that is treated as accepting their request, so you become friends at once. Their own request is never overridden by a policy check, so accept always works.
- **Remove is quiet and symmetric:** no notification, either side can no longer message as a friend; a later request starts fresh and is subject to `request_policy` again.
- **Mobile:** Friends has All and Requests tabs; Requests shows "Want to be friends" (Accept/Ignore, mutual friends, age of request) above "You asked" (Cancel). The design's swipe-to-remove is replaced by a Remove button with an inline "Keep / Remove" confirm: swipe is not reachable with a screen reader and fails the 44pt target rule when hidden. Until the Profile screen exists, the Chat/Spaces/Wallet top-left avatar opens Friends and carries a count badge for waiting requests.
Consequences: accepting from the Requests tab is the only place `declined` rows are created; block/report (trust-safety) will reuse the same row and must clear it. Owner: social-discovery-engineer

## ADR-008 · Contact matching and friend requests · 2026-11-14
Context: onboarding must show "who from my contacts is on Dyce" without ever storing the address book (SPEC §4, NDPA 2023), and without turning into a tool for harvesting who is on Dyce.
Decision:
- **Where hashing happens:** the device normalises numbers to E.164 and sends them over TLS in batches of at most 500; the **server** hashes each with the same keyed HMAC used at sign-in (`hashPhone`) and compares with `users.phone_hash`. A plain device-side hash would be trivially reversible (tiny keyspace). Numbers are not logged, validation errors don't echo them, and nothing about unmatched numbers is persisted.
- **What is stored:** only `contact_links(owner, contact_user)` for matches, upserted. `DELETE /contacts` forgets them (data deletion). Links are never removed when a contact disappears from the phone (v1: upsert only).
- **What the server returns:** for each match, the position of the number in the request plus `{ id, username, displayName, relationship }`. Never a phone number or hash. Positions let the app show the **device contact name**, which never leaves the phone. Users with no profile yet, disabled users, yourself, and anyone blocked in either direction are not returned.
- **Abuse:** matching is a membership oracle ("is this number on Dyce?"), so it is capped per user per Lagos day (`contact_lookups_per_day`, default 10,000, counted before matching and rolled back if exceeded) plus a 30/min per-IP throttle. Known limit: an authenticated, phone-verified user can still test up to the cap per day. There is no "hide me from contact matching" setting yet (not in SPEC); worth a product decision.
- **Reading national-format numbers:** contacts like `0803…` are interpreted with the **country of the user's own verified number** (stored in the session as an ISO code only), falling back to the device region. Using the device region alone silently dropped a Nigerian user's contacts on a phone set to US English (found in testing).
- **Friend requests (minimal):** `POST /friends/requests` creates a pending request, or accepts one the other person already sent (reciprocal), idempotently and race-free (advisory lock per pair). Rules: someone who blocked you looks nonexistent; you can't add someone you blocked; the target's `request_policy` applies to *new* requests (`nobody` refuses, `fof` needs a mutual friend or a contact link; accepting is always allowed); 50 new requests per day. Listing, accepting, declining and removing friends belong to the social/discovery work.
- **Find by username:** `GET /users/by-username/:username` is exact match only (no prefix search), so it can't be used to browse users.
- **Denied path:** if contacts are refused (or the platform has no address book), the screen offers "Allow in Settings" and "Find by username" and lets the user continue.
Consequences: contact matching depends on `PHONE_HASH_SALT` staying stable (see ADR-007). `expo-contacts` in SDK 58 moved its stable API to `expo-contacts/legacy`; we use that import. Owner: auth-onboarding-engineer

## ADR-007 · Phone OTP auth, sessions and the age gate · 2026-11-14
Context: Phase 1 needs sign-in with a phone number only (no passwords, no social login in v1), safe against enumeration, SMS pumping and token theft, and privacy-preserving (NDPA 2023: no raw phone numbers stored or logged).
Decision:
- **OTP:** 6 digits from the OS CSPRNG, 5 minute TTL, stored only as `HMAC(secret, challengeId:code)`; compared in constant time; one use; max 5 wrong tries then locked; only the newest code is valid. Requesting a code answers identically whether or not the number has an account.
- **Rate limits:** per phone 30 s resend cooldown, 3 per 10 minutes, 10 per day (database-backed, serialised with an advisory lock so concurrent requests can't slip past); per IP via `@nestjs/throttler` (OTP routes 10/min, refresh 30/min, everything else 120/min). A failed SMS send deletes the challenge so our provider's outage doesn't burn the user's limit.
- **Phone numbers:** normalised to E.164 with libphonenumber-js (same function in app and server), stored only as `HMAC-SHA256(PHONE_HASH_SALT, "phone:"+e164)` in `users.phone_hash`. The same secret keys OTP hashes under a different prefix. Rotating it breaks contact matching.
- **Sessions:** access token = HS256 JWT (`jose`), 15 minutes, claims `sub` and `sid` (session family); refresh token = 256-bit opaque, 30 days, only its SHA-256 stored, **rotated on every use**. Presenting an already-rotated token revokes the whole family (theft signal). We do not check revocation on every request, so a revoked session's access token can live up to 15 minutes. The app's API client therefore shares **one** in-flight refresh across concurrent 401s, since replaying a refresh token would sign the user out.
- **SMS:** `+234` goes to Termii first and falls back to Twilio; everything else uses Twilio. **Both adapters are unit-tested against recorded request shapes only; neither has been exercised against the live service**, and Termii's base URL and channel (`dnd`) must be confirmed against the account at integration time. `SMS_DRIVER=console` (dev) prints the code with the number masked. `OTP_TEST_CODE` (fixed code, no SMS) exists for Maestro and local work and the API **refuses to start** with it, or with the console driver, when `NODE_ENV=production`.
- **Android OTP autofill:** iOS uses `textContentType="oneTimeCode"`; Android relies on keyboard/autofill suggestions via `autoComplete="sms-otp"`. A native SMS Retriever / User Consent module is deferred (needs a dev build to evaluate); manual entry always works.
- **Username:** `a-z 0-9 . _`, 3-20, no leading/trailing dot, no `..`, case-insensitively unique; reserved names (`admin`, `dyce`, `support`, ...) are blocked in the schema **and** by a database trigger.
- **Age gate:** only a birth year is collected, so 19+ is treated as adult (an 18-year gap can't be told from 17 or 18). The year can be set **once** (API and a database trigger), so a minor cannot retry years until one passes. Pool staking requires `is_adult` in the ledger function itself. If the product later wants exact 18, collect a full date of birth.
- **Onboarding progress** is derived from data (profile exists, welcome grant really in the ledger) plus client-reported steps (`contacts`, `avatar`, `notifications`) so a restarted app resumes at the earliest unfinished step.
Consequences: we own OTP, sessions and abuse limits now (Supabase Auth did this before ADR-004). Apple/Google sign-in shown in the original welcome design is out of scope (SPEC §4 is phone-only). Contacts matching, the avatar builder and push registration are separate work; their onboarding screens are placeholders that can be skipped. Owner: auth-onboarding-engineer

## ADR-004 · NestJS + plain PostgreSQL replace Supabase · 2026-11-14
Context: the product owner chose NestJS for the backend and plain Postgres with SQL migrations; NestJS owns the API. The kit assumed Supabase (Postgres, Auth, Realtime, Edge Functions) plus Colyseus.
Decision: `apps/api` is a NestJS app (REST + WebSocket gateway). PostgreSQL 16+ (tests run on 17) accessed with `pg` (no ORM, so the ledger functions stay explicit SQL). Migrations are ordered `.sql` files in `apps/api/db/migrations` applied by a small runner. Auth is ours: phone OTP (Termii/Twilio adapter), short-lived JWT + rotating refresh token. Realtime chat is a NestJS WebSocket gateway. Colyseus stays for live rooms and verifies our JWT. DB tests are Jest integration tests against a real Postgres (docker compose) instead of pgTAP. File storage (avatar renders, voice notes) is S3-compatible behind a `StorageService` interface; the provider is a [HUMAN] pick later.
Consequences: we now own OTP, sessions, rate limiting and websocket scaling that Supabase provided; all "RLS" rules from ARCHITECTURE §3 become service-layer authorization plus SQL constraints. Money, ledger and fairness rules are unchanged. Hosting: any Node + Postgres host (Fly.io + managed Postgres is the default). Owner: platform-architect, supabase-backend-engineer (now owns apps/api)
