## ADR-046 · Dyce Cash is shown with the sign Ð, not the naira sign · 2026-11-24

Context: the Apple review (`Dyce/docs/APPLE_COMPLIANCE.md`, decision D2) found that a naira sign on a virtual currency can read as real money to a reviewer or a regulator (guidelines 2.3.1, 3.1.1 and 5.3). The product owner chose the sign **Ð**.
Decision: `formatNaira()` (name kept: the integer unit is still kobo, `Kobo` and `KOBO_PER_NAIRA` do not change) now prints `CASH_SIGN` = `Ð`: `Ð200,000`, `Ð12.5k`. Every user-facing string, test, flow and live document that printed ₦ was changed in the same commit; the amount field still accepts a pasted ₦ or Ð. Migration 0033 changes the one stored display mark (the Pool Shark badge). Applied migrations, dated reports (`docs/qa`, `docs/signoff`), ADRs and the status history keep the ₦ they were written with: in them it means the same amount. The app is not changed in what Dyce Cash is: virtual, not bought, not withdrawn.
Consequences: Ð is also the Dogecoin sign; it is a play-money sign here and nothing in the app is cryptocurrency (3.1.5 does not apply). Message cards already sent keep the old sign in their stored text (pre-launch data only). Owner: wallet-payments-engineer

## ADR-045 · Apple review readiness: the objectionable-text filter and the review demo logins · 2026-11-24

Context: a review of the App Store Review Guidelines (`Dyce/docs/APPLE_COMPLIANCE.md`) found that guideline 1.2 requires a filter on what people post (only requests and a thin live-room list existed) and guideline 2.1(a) requires a way for App Review to sign in (it cannot receive an SMS or an email).
Decision: (1) **`checkContent(text, 'name' | 'message')`** in `@dyce/shared` is enforced by the shared zod schemas, so the server refuses with `validation_failed` and the message `CONTENT_BLOCKED`: usernames, display names, group, space and poll titles (slurs, exploitation terms, calls to self-harm **and** profanity) and chat messages (the first three only: friends may swear). It folds accents, spacing, punctuation, repeated letters and look-alike digits; substring matching is used only for strings that are never part of an ordinary word and whole-word matching for the rest, with a test list of words that must pass (Nigeria, Niger, Scunthorpe, Kikelomo, Pedro, Dickson). The word lists are a **seed** to be extended from reports. Live-room chat keeps its own thinner check in `@dyce/games` (BACKLOG: unify). (2) **`REVIEW_LOGINS`** (up to four `identity=code` pairs, a number or an email, a 6-digit code that is not guessable) lets those identities sign in with a fixed code and sends nothing to them; every limit still applies; the accounts are ordinary; it is allowed in production on purpose and described in the review notes. It is validated at start-up (the API refuses to boot with a malformed value).
Consequences: unit tests (`content-filter.test.ts`, `review-logins.test.ts`) and PostgreSQL tests (`db/tests/review-login.test.ts`). Names already stored are not re-scanned (BACKLOG). **Needs a human:** the final word lists, the values for `REVIEW_LOGINS` and their rotation after each review. Owner: trust-safety-compliance, auth-onboarding-engineer

## ADR-044 · Email as a way in: sign up and log in with an emailed code, through Resend · 2026-11-24

Context: sign-in was a phone number and an SMS code only. People without a Nigerian SIM (or who do not want to give a number) had no way in, and SMS is the most expensive and least reliable part of auth. The Welcome and phone screens gain "Sign up with email" and "Log in with email". Migration 0032.
Decision: (1) **Same passwordless flow as the phone, one code for both sign-up and log-in.** `POST /auth/email/otp/request` then `/auth/email/otp/verify`; verifying creates the account if the address is new and finds it otherwise, so the answer to a request is **identical whether or not an account exists** (no account enumeration). The code is 6 digits, valid 5 minutes, and the limits are the phone's (30 s between codes, 3 in 10 minutes, 10 a day, 5 wrong tries then the code is locked) plus a per-IP throttle (email request 5 a minute, the rest 10). If the provider fails, the challenge is deleted so a failed send does not burn the person's limit. (2) **The address is never stored in the clear.** `users.email_hash` is a keyed HMAC (domain-separated `email:` prefix, the same `PHONE_HASH_SALT` secret as phone and OTP hashes) and `users.email_hint` the masked form (`t••••••@gmail.com`) the app shows; `email_verified_at` records the proof. `normalizeEmail` (shared) is NFKC, trimmed, lower-cased, length- and syntax-checked; **plus-addressing is kept** (`a+b@x.com` is a different identity from `a@x.com`) because rewriting provider-specific rules is a guess that would merge two people. (3) **An account has at least one identity.** `users.phone_hash` becomes nullable and a CHECK requires a phone or an email; `otp_challenges` has exactly one of `phone_hash` / `email_hash`. `anonymise_account` is redefined (0032) to clear the email fields and any email challenges as it already did for the phone. (4) **Resend over its REST API** (`POST /emails`, bearer key, `Idempotency-Key: otp-<challengeId>` so a retry cannot send two codes, 8 s timeout, two retries on 429, 5xx and network errors). Provider errors never carry the address, the code or the key; the shared `redact.ts` now scrubs email addresses and `email` keys from logs and Sentry. Drivers: `console` (prints the code, address masked; development only) and `resend`; **production refuses `console` while email auth is on**. (5) **`EMAIL_AUTH_ENABLED`** (default true) turns the routes off (404 `email_auth_disabled`); `GET /auth/methods` tells the app, which hides the email buttons. `OTP_TEST_CODE` (development) applies to email too. (6) **Linking a second way in.** A signed-in person can add an email to a phone account, or a phone to an email account (`/me/email|phone/request|verify`); an address or number already used by another account is `identity_taken`. `/me` returns `signIn {phone, emailHint}` for Settings.
Consequences: 29 PostgreSQL tests (`db/tests/email-auth.test.ts`: sign-up, log-in, limits, lock, linking, taken, deletion, no clear-text storage), unit tests for the address rules, the provider and the env checks, an HTTP end-to-end run against a mock Resend (`pnpm -F @dyce/api e2e:email`: request shape, idempotency, retries, errors, logs and database free of the address and code, throttle, disabled mode, production refusal), and an app flow (`e2e/12-email-signup-login.yaml`). **Not done / needs a human:** a real email to a real inbox (Resend account, verified domain, SPF, DKIM, DMARC: `Dyce/docs/SETUP_GUIDE.md` section 4); bounce and complaint webhooks; blocking disposable-email domains; telling the old address when an email is changed; any recovery for a person who loses both their email and phone. Owner: auth-onboarding-engineer, trust-safety-compliance

## ADR-043 · The Ludo room: Ludo for 3 or 4 at a table in a Space · 2026-11-24

Context: the async Ludo (ADR-035) is two players in a chat; GAMES.md has Ludo as "Async 2p / Live 3-4p". `games.sync` is per slug, so a live table needs its own row. The generic `turns` room (Whot!, Crazy Cards, ADR-025) already did everything else a Ludo table needs, so this was a small step, not a new room type. Migration 0031.
Decision: (1) **`ludo-room`** is a `turns` entry in `LIVE_GAMES` (`packages/games/src/live.ts`): the same `ludoEngine`, `cfg {tokens: 4}`, **3 to 4 seats** (two players play the async game), `turnMs` 25 s **per action** (a turn is a roll, then a move, each on the clock), `autoAction = ludoAutoAction` for a seat that runs out of time or leaves, all three payout schemes (a finished game places the first home first and ranks the rest by progress, ties share a place, so 50/30/20 and 60/40 work), no quick match. (2) **A `games` row** `ludo-room` ("Ludo room", live, 3D, 3-4 players, `{board,spaces}`, Pool minimum ₦500 as for Ludo, Pool **on**). It is not in the async registry, so it never shows in the chat's Games drawer; it is made from Create a space. (3) **The app** reuses the chat game's `LudoBoard` inside `LudoTable` (the room's seats, who is on the clock and for how many seconds, the leave sheet that states the Pool consequence, the results panel with each payout), chosen in `TableScreen` for the slug; "Ludo" is a tile in Create a space. (4) **Money rules are the generic room's, unchanged:** a seat that leaves, or is away for the reconnect grace, **forfeits its seat fee and is placed last**; a game with one seat left ends at once; settlement is `settle_or_hold` (the collusion check, ADR-039) from `PgLiveMatchStore.finish`.
Consequences: proven on a real Colyseus room on real PostgreSQL (`apps/game-server/test/ludo-room.test.ts`: a Free table of 4 and a **Pool table of 3 at 50/30/20 played to the end** with every wallet checked and the escrow at zero, a seat that leaves forfeiting, seat limits) and by engine tests (`live.test.ts`: a whole game at 3 and at 4 seats with only the auto action). In a browser: three seats, the table, the roll. Not done: a **4-device or 4-phone run**, a Ludo-specific turn-timeout run in a real room (the generic room's auto-play is tested with Whot!), a Ludo room quick match (not offered), Hermes determinism of the dice (the engine's own open item). Owner: realtime-spaces-engineer, games-3d-engineer

## ADR-042 · Streak lost and the streak saver · 2026-11-24

Context: SPEC §9: streaks are "consecutive days with a win" and "**Streak saver:** lose a streak and you get 24h to win one game to restore it". ADR-023 kept the streak (and left an unused `saver_expires_at`), but nothing noticed a streak ending, so the design's StreakLost screen had no data (BACKLOG). The design says "Win your next free game within 24h and the 4 comes back" and names who "broke it". Migration 0030.
Decision: (1) **When a streak ends.** It is alive on the day of the last win and the day after (Lagos days); when a whole day passes with no win it **ends** on the first day without one (`lost_on`). `_streak_roll(user, day)` notices it, idempotently, from three places: an **hourly sweep** (`streak_sweep`, run by the API), **any win** (so a win that arrives before the sweep still sees the loss: a win's day, not the wall clock, is what counts, which keeps retroactive finishes honest), and **opening the streak screen** (`streak_check`). Noticing it sets `current = 0`, records `lost_length`, `lost_on`, `lost_to` and sends a `streak_lost` notification (list only, not pushed; only while it still matters, not when noticed weeks late). A streak of **one day** is not worth a screen: it resets silently (`streak_saver_min_length`, 2). (2) **The saver (money-free, XP and badges untouched).** For a streak of 2 or more that ended, **one Free win on the next Lagos day restores the old length** (`current = lost_length`, that win counting as the day's win, so the next day's win makes it one longer). The window is that whole Lagos day, which is **at most 24 hours from the moment the loss is noticed** and ends at the next Lagos midnight; the screen says how many hours are left. **A Pool win does not use it** (the design says "free game"; the streak itself still counts Pool wins), and a loss or draw does not. **It is used once**: after a restore the next one is offered only after `streak_saver_cooldown_days` (7), so a streak cannot be saved every week by a missed day. A saver that is not offered (cooldown) is said so on the screen. (3) **"Amaka broke it"**: `lost_to` is the opponent of the person's most recent 1v1 loss on the day it ended, if any, so the rematch button has someone to point at; with no such loss the screen says "A day went by without a win." and offers "Play a free game". (4) **API.** `GET /me/streak` (`StreakStatus`: current, best, won today, the lost streak with its saver, the longest streak among friends for the design's "Longest among your friends") and `POST /me/streak/seen` ("Not now"). The app shows the card once, on the result of a Free game (`StreakPrompt`), and from the notification (`/streak`); the server remembers it was seen. (5) The award trigger `_trg_match_progress` is replaced (same body) so the streak is kept by `_streak_win`; the API role still cannot write `streaks` or call the helpers (tested).
Consequences: `db/tests/streak-saver.test.ts` (15 tests on real PostgreSQL: keeping a streak, noticing the end by look, by sweep and by a win, who broke it, no screen for a one-day streak, seen, a Free win restoring, a loss, draw and Pool win not restoring, the saver gone after its day, once and then a cooldown, permissions, friends' best), app unit tests for the copy and the prompt rule, a browser check in both themes. **Needs a human:** the product call on three things the SPEC does not say: the saver is Free-win only, one per week, and for streaks of 2+. "Streak at risk" push (SPEC §12) is not built (BACKLOG). Owner: social-discovery-engineer, game-platform-engineer

## ADR-041 · Pool for every async game, the 24 hour turn clock, and per-match options · 2026-11-24

Context: ADR-018 built Pool on the async match service but only the reference game Pig had `supports_pool`; ADR-019 and ADR-036 left Word Hunt, Cup Pong and the 15 Phase 4 games Free until a Pool match of each had been played through settlement. The sign-offs (Phase 2 and 4) named that, and "Mancala (Kalah) cannot be created" (no per-match option). Migrations 0026 to 0029.
Decision:
- **What Pool means for an async game (one rule for all, written down so a human can review it).** Both players stake the same amount (the higher of the platform minimum ₦100 and the game's minimum from GAMES.md); the creator's is locked on send, the invitee's on accept; the winner takes the whole pot; **a draw refunds both**; an unanswered invite refunds (24 h, ADR-018); **resigning loses** (the other player takes the pot); **a player who does not move for 24 hours forfeits** (SPEC §9, `pool_turn_hours`); **if both players were due and nobody moved, every stake is refunded** and the match is cancelled. Every one of those ends in `settle_or_hold` (a win, a resign, a forfeit) or `refund_match` (a refund), never a new way to move money, so **the ADR-039 collusion check runs on every settlement** (tested for a played-out result, a resignation, a late move and the clock).
- **The turn clock (new; async matches had no timer at all, which let a losing player lock a Pool pot forever by not moving).** Pool only: `matches.turn_deadline` is set to now plus `pool_turn_hours` when the game starts and after every move, and cleared when it ends. The player(s) `engine.currentPlayers` returns are the ones on the clock. Settled three ways, under the match row lock so it happens once: `MatchesService.forfeitOverdueMatches` every 5 minutes, **when anyone opens an overdue match**, and **when a move arrives late** (the move is not applied; the caller gets the finished match). One player on the clock = that player forfeits. Both on the clock (Word Hunt, Anagrams and Sea Battle's placing both play at once, and nobody has moved) = **refund, status `cancelled`**. A Word Hunt where one player has finished and the other never started therefore ends in a forfeit by the one who never started. **Free matches have no clock** (nothing is at stake, and SPEC asks only for Pool). The deadline is shown to both players (`MatchView.turnDeadlineAt`, the host's "Alice QA forfeits in 23h 10m without a move") and the mode sheet says it in plain words ("No move for 24 hours is a forfeit"). A forfeit is stored in `live_meta` (`forfeitedBy`, `forfeitReason: timeout|resign`); after `settle_match` the loser's result reads `loss` (as it already did for a Pool resignation: `settle_match` rewrites it); an integrity hold keeps `forfeit`.
- **Pool is on for 16 games** (migrations 0027 to 0029), each played to the engine's own result in a Pool match in `db/tests/pool-async-games.test.ts` (wallets before and after, the pot to the winner or both stakes back on a draw, the escrow `settled`, `ledger_check_invariants` clean), and also settled by resigning and by the turn clock: **Word Hunt, Cup Pong** (batch 1); **Anagrams, Filler, Tanks, Mini Golf, Darts (501), Basketball, Archery, 8 Ball** (batch 2); **Chess, Checkers, Ayo (and its Mancala mode), Dots & Boxes, Ludo (two players), Sea Battle (classic and salvo)** (batch 3). Pool minimums are GAMES.md's (₦100 to ₦500) and the drawer's stake chips start at the higher of those and the platform minimum.
- **Left Free, recorded:** (1) **Word Tiles**: the engine's own owner says the in-repo word list (about 5,500 words) is a stand-in and a bigger one must be loaded before Pool (ADR-031); with money on a play, a real word the server refuses is a bad loss, so it stays Free until `WORD_TILES_WORDLIST_FILE` and `_ID` point at a full list in production. (2) **Darts "Around the clock"** is a **free variant** in GAMES.md: `pool: false` on that choice, so it is refused as Pool (`pool_not_supported`) and the mode sheet says "Free only for this variant"; Darts 501 is Pool. **Hidden information after a resign or forfeit** (the case the task asked to check): resigning and forfeiting are decided by the service, not the engine, so the state is not terminal and `view()` reveals nothing new (Sea Battle's fleets and Word Hunt's words stay hidden; this is argued from the code, not covered by a test of its own). **Accepted risks, not blockers:** Word Hunt and Anagrams can be solved by a program (the same dictionary and grid are public code; the integrity layer's timing signal needs 3 s between Start and Submit, which a solver can wait out), and Chess, Checkers and Word Tiles can be played with an engine; stakes are capped (₦20,000, ₦100,000 a day), the games are 18+, and the cash is virtual (BACKLOG: a "perfect score" and "engine-like play" signal).
- **Per-match options.** `CreateMatchRequest.options` (and `matches.options`) carry a variant. Each registry entry lists what it offers (`EngineEntry.options`: key = the engine `cfg` key, the allowed values, a label, a note, and **whether that variant can be played for stakes**); `resolveOptions` accepts only those keys and values, lays them over the entry's `cfg`, dry-runs the engine's `init` (the engine's own config check has the last word) and stores only values that differ from the default, so "no option" and "the default" are the same match and a retried create with the other spelling is not `message_id_taken`; a different option on a retry is. `GET /games` returns `options` for games that have them; `MatchView` and the card payload carry `options` and `variantLabel` ("Mancala (Kalah)"). Offered: **Ayo (Ayo, Mancala (Kalah))**, **Darts (501, Around the clock)**, **Sea Battle (Classic, Salvo)**. The mode sheet shows a "Rules" row for them, and a rematch keeps the variant.
Consequences: `@dyce/shared` gains `matchOptionsSchema`, `GameOption`, `MatchView.options/variantLabel/turnDeadlineAt`, `GameCardPayload.variantLabel`; the app consumes them. New config `pool_turn_hours` (24). New cron: the 5-minute sweep also settles overdue Pool matches. Migrations are expand-only. **Needs a human (money rules, not guessed beyond this):** (1) the **24 hour forfeit** and the **both-idle refund** (the alternative for a match nobody moved in is a forfeit of both, which keeps a pot with nobody); (2) the **per-game Pool list**, above; (3) a **shorter turn clock for fast games** (a Cup Pong throw is a second of work and 24 hours is long; one number is the simplest rule and a per-game one is a config row away); (4) a lawyer's read of "no move for 24 hours is a forfeit" (Dyce `docs/RELEASE_CHECKLIST.md`). Owner: game-platform-engineer, wallet-payments-engineer

## ADR-040 · Operations: images, probes, graceful shutdown, structured logs, Sentry, and the nightly ledger check · 2026-11-23

Context: the backend had CI and a health route but no way to ship, no readiness, no structured logs, no error reporting and no scheduled money check (BACKLOG). Phase 5 needs all of them with no cloud account available.
Decision: (1) **Two images** (`apps/api/Dockerfile`, `apps/game-server/Dockerfile`), build context the repository root, multi-stage (deps, build, prod-only node_modules, runtime as user `node`), Linux-only pnpm architectures so the Windows and macOS binaries of `embedded-postgres` and turbo are not downloaded. The API image also carries `db/*.ts`, run with Node's native type stripping (`node db/migrate.ts`, `node db/ledger-gate.ts`), so there is no separate migration build. **Migrations are a separate deploy step run as the owner role** (`MIGRATION_DATABASE_URL`), before the new code starts; the services connect as `dyce_app` (`deploy/postgres/init-roles.sql`). Migrations must be expand-only so a rollback runs old code on the new schema. (2) **Probes:** `/health/live` (process only, never the database), `/health/ready` (database up and not draining; returns `release` and the newest `schema`), `/health` kept. Both exempt from the rate limit. The game server has the same two. (3) **Graceful shutdown is handled in `main.ts`, not with `enableShutdownHooks()`**: Nest re-raises the signal after cleanup, which made a clean stop exit 143 and look like a crash. SIGTERM flips readiness to `draining` for `SHUTDOWN_DRAIN_MS`, then `app.close()` (HTTP, WebSocket hub, pool), exit 0; a hard timeout exits 1. (4) **One redactor** (`packages/shared/src/redact.ts`) for logs, Sentry hooks, alert text and the app: phone numbers (E.164 and Nigerian local forms), JWTs, bearer tokens, credentials in URLs, sensitive keys and sensitive query parameters. The logger writes one JSON line per event with `service`, `release` and the request id (`X-Request-Id`, accepted only if short and boring); the access line carries the **route pattern, never the URL**; stray `console` calls are routed through the redactor; Nest's per-route startup chatter is demoted to debug. (5) **Sentry (`@sentry/node` v11) behind `SENTRY_DSN`**: not even imported without it; `dataCollection` turns off user info, cookies, headers, bodies and query strings, and `beforeSend` scrubs the rest. A catch-all filter (registered first so `DyceErrorFilter` keeps priority, checked by `scripts/ops-check.mjs` because Jest cannot load ESM-only Nest) logs and reports only 5xx. (6) **Nightly `ledger_check_invariants`** at 02:15 Africa/Lagos in the API, with a catch-up at boot if the last run is over 26 hours old, a **transaction-scoped advisory lock** (one instance runs it, and it is safe behind a transaction pooler), every run recorded in append-only **`ledger_check_runs`** (migration 0024), a critical alert on any problem or on the check failing to run (webhook, Sentry fatal, log), Pool frozen for wallet mismatches (`LEDGER_CHECK_FREEZE`), and a heartbeat ping after clean runs for a dead-man's-switch monitor. **`db/ledger-gate-logic.ts` evaluates the launch gate**: a non-clean run or a hole of more than 36 hours resets the streak. (7) **`docker-compose.yml`** runs Postgres, the migration, the API and the game server in the production order with development-only secrets. (8) **Still one API instance and one game server.** The hub, the throttler counters and the game rooms are in memory; a second replica needs Redis behind `RealtimeHub.publish`, shared throttling and a room matchmaker (Dyce `docs/RUNBOOK.md` section 12). (9) `deploy/production.env.example` documents every variable and a unit test fails when the API schema gains one that is not documented.
Consequences: verified on Windows and in Docker on Linux locally; never on a real platform. `msgpackr-extract` is set to `false` in `allowBuilds` (a pnpm 11 build-script prompt that blocked frozen installs). The compose and image builds, the smoke script (Sentry off and on) and the ledger check are in CI. The Docker build showed that `pnpm install --prod` needs `CI=true` without a TTY. Open for a human: hosting, the monitoring accounts, the alert route and on-call, restore rehearsals (Dyce `docs/RELEASE_CHECKLIST.md`). **A credential committed in `apps/game-server/.env.example` (commit 9c36e70) was replaced with placeholders but is still in git history: rotate it.** Owner: release-engineer.

## ADR-039 · The integrity layer: Pool signals and payout holds, the request spam filter, the moderation queue, the device check, rate limits · 2026-11-23

Context: Phase 5 (SPEC §9, §11, §13). ADR-013 left moderation, outcomes and any Pool hold undone; ADR-017/018/022/025/037 left collusion signals and holding a payout for "when an anti-cheat flag exists". Server-authoritative moves and re-simulation were already there (ADR-016/017), so what was missing is *detection*, a *money rule for a held payout*, and the *people tooling*. Migration 0025. Tests: `db/tests/integrity.test.ts` (58) and `integrity-callsites.test.ts` (5) on real PostgreSQL, 21 unit tests, `db/tests/rate-limits.test.ts` (6), `scripts/integrity-e2e.mjs` (real HTTP), and a live Pool match in the game server (`test/room.test.ts`). Ledger invariants are checked after every test that touches money.
Decision:

- **Signals, not verdicts.** `integrity_evaluate_match(match)` runs once, when a Pool match would settle, and writes `integrity_signals` (kind, score 20..100, subject, other, match, detail, `flagged`). Signals never ban, mute, suspend or move money on their own. Detail never contains a hash, IP or device value. A match's score is the sum of its signals, capped at 100: at or over `integrity_flag_threshold` (40) the signals are *flagged* (they appear in the moderation queue); at or over `integrity_hold_threshold` (70) the payout is held. Kinds and weights (limits are `app_config`): `pair_repeat` (the same two accounts in 5+ Pool matches in 7 days: 30, +10 each more, max 60), `pair_one_sided` (4+ decided meetings in 14 days and one side won every one: 30), `shared_device` (same install in 30 days: 60), `shared_ip` (same connection in 7 days: 25), `feeder_account` (a loser under 7 days old, 3+ matches against the same winner and 80% of their Pool games: 50), `feeder_network` (a winner paid by 3+ accounts under 7 days old in a week: 40), `timing_impossible` (3+ moves faster than the game's `min_gap_ms`: 45), `input_repeat` (the identical input `max_repeat` times in a row: 25), `cheat_reports` (an open cheat report from the opponent: 40; from 3 different people: 30), `attestation_failed` (a failed device check in the last week: 40). Per-game timing rules are rows in `integrity_game_rules` (seeded: Word Hunt / Anagrams 3 s between your own Start and Submit, the physics games 300 ms and 6 identical inputs, the board and card games 200 ms; party games none). Free matches are not judged. **The weights and limits are our first guess, with no real traffic behind them**: tune them with the first weeks of data (BACKLOG).
- **Who is who: keyed hashes only.** `user_fingerprints` holds HMAC hashes of the app's install id (`x-dyce-device`, a random id the app makes, not a hardware id) and of the client IP (IPv6 reduced to its /64, IPv4-mapped to IPv4), recorded only when someone enters Pool (`PoolEntryGuard` on create / accept / counter / space create / space join / quick-match join). Kept 90 days (`fingerprint_retention_days`, a nightly prune), deleted at once when an account is deleted (trigger on `users.disabled_at`). Mobile networks put many people behind one IP, which is why a shared IP is weak (25) and a shared install strong (60).
- **The money rule for a held payout (new; ADR-012/016/018 do not cover it, SPEC §9 allows it only for flagged results).** Every settle path (`MatchesService` final move and resign, the game server's `PgLiveMatchStore.finish`) now calls `settle_or_hold(match)` instead of `settle_match`. For Free and for a Pool match under the hold line it *is* `settle_match`. Over the line it records an `integrity_holds` row and stops: **the escrow stays open and nothing moves**, `matches.status` becomes `disputed` (an existing value; the app shows it as a finished match whose payout is pending, `payoutKobo` null), and each staked player gets a `moderation_notice` ("being checked", never the reason). Placements and results stay as the game decided. A person then decides, through `resolve_integrity_hold` (admin role only, audited, idempotent, serialised by the match row lock): `release` = `settle_match` as decided (signals dismissed); `void` = `refund_match` ("cancelled": every stake back, results cleared); `disqualify <player>` = that player is placed last and forfeits, the others keep their order, then `settle_match`. **No new way to move money**: only `settle_match` and `refund_match`, called from inside the function. A hold nobody decides within `integrity_hold_max_hours` (72) **releases as originally decided** (`integrity_lapse_holds`, every 10 minutes, audit name `system:lapse`): a stake must not be stuck behind a moderator who is away, and the original result was the server's own. A hold applies only *before* settlement; a payout already made is never clawed back by a signal (that remains the dispute path and its open money question, ADR-037). To make the deferred constraint trigger `ledger_txn_balanced` work for the moderation role it is now `SECURITY DEFINER` (it only reads).
- **The request spam filter.** A first message or request to a non-friend is scored by `scoreRequest` (pure, unit tested) from facts read when it is sent: sender account age under 24 h (+30), 8+ new stranger chats in the last hour (+40), 3+ different people declined them in 30 days (+40), reports for spam / abuse / scam by 1 (+30) or 3+ (+60) different people in 30 days; at 50 the request goes to the recipient's **filtered** bucket (`conversation_members.filtered_at`, `filter_reason`). Someone who has the sender in their contacts, or shares a friend with them, is never filtered. Sticky until the recipient answers (accepting or declining clears it). A filtered request is **not deleted, not blocked, and the sender is not told**: it is not counted in `requestCount`, is not pushed live, and shows behind `GET /conversations?filter=filtered` and `filteredCount` ("N filtered as spam · view" under Requests, the design's footer). Accept, decline, open and block work as usual. Friend requests and money-card chats are not scored (BACKLOG).
- **The moderation queue.** Admin-only, no UI: JSON endpoints under `/admin/moderation` and `apps/api/scripts/moderation.mjs`. It is off (404) unless both `ADMIN_DATABASE_URL` (a login role in the new NOLOGIN role `dyce_admin`) and `ADMIN_TOKENS` (`name:token`, 32+ characters, name written to the audit log, `system` reserved) are set; the public API's pool cannot read the views or call the functions (tested), and the moderator role cannot read tables or reach `settle_match`, `reverse_txn` or `resolve_dispute` directly (tested). Reads: views `moderation_report_queue`, `moderation_signal_queue`, `moderation_hold_queue`, `moderation_dispute_queue`, `moderation_user_overview`, `moderation_audit`. Writes, each one writing `moderation_actions` in the same transaction (the table rejects UPDATE, DELETE and TRUNCATE): `moderation_act_on_report` (`review`, `warn`, `mute`, `suspend`, `dismiss`), `moderation_sanction` / `moderation_lift_sanction`, `moderation_review_signal`, `resolve_integrity_hold`, `moderation_resolve_dispute` (ADR-037's `resolve_dispute`, audited; `reversed` still needs a reversal posted by hand). **Sanctions**: `warning` (a notice), `mute` (default 7 days, up to a year: no messages, friend requests or money requests; they can still play and report; `account_muted`) and `suspension` (no new session, refresh tokens revoked, Pool frozen until lifted unless something else froze it; `account_suspended`; a current access token lives out its 15 minutes). **The reporter's outcome** (ADR-013): closing a report sends the reporter one `report_outcome` notification, "actioned" or "dismissed", never what was done. Actions on the same report twice are `report_resolved`.
- **The device integrity gate.** `IntegrityGate.poolEntry` records the fingerprints, then, if the app sent `x-dyce-attestation`, verifies it through an `AttestationVerifier` against a stateless nonce from `POST /integrity/challenge` (HMAC per person, valid 5 minutes). `INTEGRITY_DRIVER=dev` passes everything and **the API refuses to start in production with it**; `store` is the production driver and is a **stub that fails closed** (`not_configured`). With `integrity_required` false (the default) a missing or failing token is only an `attestation_failed` signal; with it true, Pool entry is refused with `integrity_check_failed`, and a verifier that throws counts as a failure. **Human-gated integration**: Play Integrity needs a Play Console app linked to a Google Cloud project; App Attest needs an Apple developer account and the attestation-key storage; the app needs the native modules and to send the headers. Until then production runs with `INTEGRITY_DRIVER=store` and `integrity_required=false`.
- **Rate limits.** `docs/RATE_LIMITS.md` lists every limit. New: signed-in requests are counted **per account** (`throttleTracker`, `UserThrottlerGuard`) and everyone else per address, because carrier-grade NAT puts whole neighbourhoods behind one IP; a token that does not verify falls back to the address. `POST /matches/:id/accept` (30/min) and `/counter` (20/min) gained limits; `POST /integrity/challenge` 20/min; the admin API 60/min.
- **Quick match.** Pool never pairs two accounts that share a device or IP fingerprint (`users_share_fingerprint`); everything else (pair repeats, feeders, timing) is judged at settlement like any match.
  Consequences: shared schemas gain `ConversationFilter` `filtered`, `ConversationsResponse.filteredCount` and the notification kinds `report_outcome` and `moderation_notice`; the app maps them (Requests footer, notification tag and copy, error copy for `account_muted`, `account_suspended`, `integrity_check_failed`). New env: `INTEGRITY_DRIVER`, `ADMIN_DATABASE_URL`, `ADMIN_TOKENS`. New codes: `account_muted`, `account_suspended`, `integrity_check_failed` and the SQL ones (`hold_not_found`, `hold_resolved`, `invalid_decision`, `report_not_found`, `report_resolved`, `sanction_not_found`, `signal_not_found`, `dispute_not_found`, `admin_required`, ...). Not built (BACKLOG): the app sending the device headers and the attestation token, a moderator UI, retroactive holds on a settled match, game moves attached to reports, bot and automation detection beyond timing and repeats, scoring friend requests and game invites.

Needs a human (money, people and law, not guessed here): (1) **The lapse rule**: a hold nobody decides releases as originally decided after 72 hours; the alternative (void and refund) is kinder to a colluder's victim and harsher to an honest winner. Someone must own the queue (a daily check) or holds will simply lapse. (2) **Thresholds and weights** need real data; start with `integrity_hold_threshold` high and watch the flagged queue first. (3) **Sanction policy** (how long a mute, when a suspension, appeals) is not in the SPEC; the tools exist, the policy does not. (4) **NDPA**: device and IP hashes, sanctions, signals and the audit log are personal data kept for abuse prevention (lawful basis: legitimate interest); the privacy notice must say so and a retention period for signals, sanctions and the audit log (only fingerprints have one) needs to be decided. (5) **Play Integrity and App Attest** accounts and the verification code. (6) **Provisioning**: creating the `dyce_admin` login role and the moderator tokens, and keeping the admin API on a private network. Owner: trust-safety-compliance

## ADR-038 · Group chats, practice bots, replies, reactions, deletes and polls · 2026-11-22

Context: SPEC §5 (Groups and Bots filters, bots as practice partners) and §6 (replies, reactions, delete for me / for everyone within 15 minutes, groups of up to 50 with a name, polls and "start a Space from the group") had no server side; ADR-010 deliberately left them out. Migration 0022 (`conversations.bot_slug`, `conversation_members.joined_at`, `message_hides`, `poll_votes`, a CHECK on `reactions.emoji`, a title CHECK, config). Tests: `db/tests/groups.test.ts` (47, real PostgreSQL) plus the existing `messages.test.ts` (one test now describes tombstones).
Decision:

- **One model for three shapes.** `conversations.kind` is `direct` (ADR-010, unchanged), `group` or `bot`. `ConversationSummary` is a union on `kind` (`peer` | `group` | `bot`); `GET /conversations?filter=` now takes `all | friends | groups | requests | bots`. Groups and bots never have a `request` state and never appear in Requests or its count. `All` lists direct chats, groups, and the bots you have said something to; `Bots` lists all four (created, with a greeting you have already read, the first time you ask: no badge from four greetings).
- **Strangers never land in Chat.** You can only add **your friends** to a group (`group_member_not_friend`), so nobody is put in a group, and so in their Chat, by a stranger. Someone who blocked you looks like a user who does not exist (`user_not_found`); one you blocked is `blocked`. Blocking after the fact does not remove anyone from a group, but **messages from people you blocked are hidden from you and not pushed to you** (history, last-message preview and unread count all skip them).
- **Group rules** (SPEC gives only "up to 50 members, name and photo"; the rest is our call). The creator is admin. Needs two other people (a group of two is a direct chat). Admins add friends, remove non-admins, rename, and make members admins; **an admin can only step down themselves, never while the only admin (`last_admin`), and admins cannot remove admins**, so nobody can take a group from its maker. Anyone can leave (idempotent); if the last admin leaves, the longest-standing active member (`joined_at`, then id) becomes admin. Removing and leaving set the member to `left` (the row stays so old messages keep their sender's name); being added back resets `joined_at`. **A member sees a group's history only from when they joined** (`joined_at`, set from the server clock in code, never the column default). 50 members and 10 groups created a day are `app_config` (`group_max_members`, `groups_created_per_day`). All changes to one group run under an advisory lock (the limit and the "always an admin" rule hold under racing adds and leaves; tested) and post a centred `system` line ("Tunde added Amaka and Dayo") that everyone gets live. Group creation takes a client id and is idempotent (an id from someone else, or a direct chat's id, is `group_id_taken`). **Group photos are a placeholder**: `photo_url` exists but there is no upload service (BACKLOG); the list shows a cluster of the first three other members' avatars.
- **Replies.** `messages.reply_to` (existing column); `replyTo` on send must be a live message of the same conversation (`message_not_found`). Messages come back with a `replyTo` preview `{senderId, senderName, snippet, deleted}` so a quote needs no second request; a quote of a message deleted for everyone shows "This message was deleted".
- **Reactions.** One per person per message (the existing primary key), from a fixed set of keys `gg | ha | wow | q | l` (CHECK), drawn by the app as text chips (the design's GG, HA, !!, ?, L; no emoji as UI). `PUT /conversations/:id/messages/:mid/reaction {reaction|null}` is idempotent; the live `reaction` event carries the whole tally so a client that missed one still ends right. Not allowed on system lines or deleted messages, by someone who left, in a blocked pair, or in a request you have not accepted (reading is allowed, answering is not).
- **Deleting.** *For me*: a row in `message_hides`, any message, any time. *For everyone*: your own **text or poll**, within `delete_for_everyone_minutes` (15, SPEC), `delete_window_closed` after; the row stays as a **tombstone** (`deleted_at` set, body and payload wiped, poll votes deleted, a CHECK keeps the text rule for live rows only) so threads, replies and reports keep their place. Money and game cards can only be hidden for yourself (they are records). The first message-count check in a request now **includes deleted messages**, so delete-and-resend cannot get round `request_messages_before_accept`. A moderator report snapshots messages at report time, so evidence survives a later delete. `message_deleted` events go to everyone (`everyone`) or only your own devices (`me`).
- **Polls (groups only).** `POST /conversations/:id/polls {id, question, options[2..6]}` stores the question and options in the message payload and `body = "Poll: ..."`; `poll_votes` holds one vote per person (changeable, or `null` to take back). Reads return counts and *your* `myVote`; the `poll` event carries the tally and who voted, and the voter's own devices set `myVote` from it. A `poll` on a direct chat is `not_a_group`.
- **Bots: scripted on the server, no AI.** Coach Cue (8 Ball), Quiz Mama (trivia), Word Hunt Trainer and Admiral Ade (Sea Battle) are 1:1 `bot` conversations (metadata in `@dyce/shared` `BOTS`, scripts in `apps/api/src/chat/bots.ts`). A reply is a keyword rule or a rotation of fallback lines; Quiz Mama keeps the open question in the payload of her last message, so a quiz survives restarts with no extra table. **No model call, no cost, nothing leaves our servers**: this is the cheapest thing that makes the screen real, and an LLM (with a cost cap, a moderation pass and a prompt-injection review) can replace `botReply` later without touching the schema. Replies arrive after ~0.7 s so they read as typing; each reply's id is derived from the user message id, so a retried send never produces two. A bot's messages have `sender_id NULL` and come back with `senderId = "bot:<slug>"`. Bots are Free-only practice partners as SPEC says: they cannot be sent money or games, reported or blocked, and have no read receipts or typing. Starting a real practice *game* against a bot is not built (BACKLOG).
- **Realtime.** New events `reaction`, `poll`, `message_deleted` (`scope: me|everyone`) and `conversation` (`updated | removed`: your group changed, or you are out of it). Typing now goes to **every other active member** of a group (`typingTargets` replaces `typingTarget`; the socket server publishes to a list). Group events skip members who blocked the actor. Group read state is per member and has **no read receipts**.
- **Rate limits.** Per-route `@Throttle` (create group 10/min, polls 20, reactions and votes 120, member changes 30, deletes 60, sends stay 60) on top of the daily group cap; stranger limits are unchanged.
- **Money, games and spaces are untouched.** `postCard`, game cards and `playablePeer` still need a direct chat (a group fails with `conversation_not_found`), so no money card or game card can land in a group; a Space card inside a group thread is in the BACKLOG. Search and notifications are unchanged (no push for new messages yet, ADR-010).
  Consequences: the app gets `ConversationSummary` as a union (use `.kind`), `Message` gains `system` and `poll` kinds plus `replyTo`, `reactions`, `deleted`, and the query key `groupMembers`. New error codes `not_group_admin`, `group_full`, `group_id_taken`, `group_member_not_friend`, `groups_rate_limited`, `message_not_found`, `cannot_delete_message`, `delete_window_closed`, `invalid_vote`, `not_a_group`, `last_admin`. `MessagesService` takes `{ botReplyDelayMs }` (tests use 0 and `bots.idle()`). Owner: messaging-engineer

## ADR-037 · Edge flows: resigning, Pool disputes, account deletion, the data export, and why you are out of a space · 2026-11-22

Context: SPEC section 9 (disputes), 12 (delete account: balance cleared, games history anonymised; download my data) and 7 (space edge cases) had no server side, and the app's game menu needs a way to give a game up. Migration 0023. Tests: `db/tests/edge-flows.test.ts` (18, real PostgreSQL, `ledger_check_invariants` after each).
Decision:

- **Resign.** `POST /matches/:id/resign` (`MatchesService.resign`): an active 1v1 match only (`match_not_open` otherwise, `resign_not_supported` with three or more players). The resigner gets placement 2 and `forfeit` (Pool: `settle_match` turns it into `loss`), the other player placement 1 and `win`, `live_meta.resignedBy` is recorded, and the match settles through `settle_match` like any result, so a Pool pot goes to the opponent in the same transaction. A retry by the resigner is a no-op. This is independent of an engine's own resign action (Chess and Checkers have one): the menu works for every game.
- **Disputes** (`DisputesService`, `GET|POST /matches/:id/dispute`). One per player per match (`UNIQUE (match_id, user_id)`; asking again returns the same one). Allowed for a finished Pool match you played, until `dispute_window_hours` (24, SPEC; the design's 48 loses to the docs) after `finished_at`; at most `disputes_per_day` (5) a day. Reasons: cheat, glitch, score, disconnect, other (CHECK). Status: `open`, `reviewing`, `upheld` (the result stands) and `reversed` (the result was corrected), with a CHECK that a resolved dispute has `resolved_at` and a reversed one has a `resolution_txn`. **Opening a dispute moves and freezes nothing.** SPEC says a payout is held only when the server's anti-cheat flagged the result, and no such flag exists yet (BACKLOG), so the design's "pot frozen" step is not told. Moderators read `moderation_dispute_queue` (view, no access for the API role) and move a dispute with `resolve_dispute(...)` (admin only, not granted to `dyce_api`). A correction is a separate `reverse_txn` by an admin, whose id `resolve_dispute('reversed')` requires; `reverse_txn` fails with `insufficient_funds` if the winner already spent the pot, and what to do then is a **human decision** (see below).
- **Account deletion** (`AccountService`, `GET /me/deletion`, `POST /me/delete {username}`, `POST /me/delete/cancel`). Typing the username confirms. `request_account_deletion` records `execute_after = now + account_deletion_grace_days (30)` (the design's grace period; SPEC is silent) and revokes every refresh token; asking again keeps the date; **verifying an OTP for the account cancels it** (`AuthService.verifyOtp`), which is the design's "log back in and everything comes back". A nightly job (`AccountMaintenance`, 03:30) runs `processDue`, which for each person calls the Spaces service to leave any *waiting* space (host hand-over and refunds stay in one place) and then `anonymise_account(user)`: idempotent (a finished one returns true and changes nothing, tested), it returns false and waits while the person still sits in a live space; cancels their open matches (Pool stakes of everyone go back first via `refund_match`); cancels their open payment requests; clears the balance with **one balanced `adjust` transaction against `system_adjust`** keyed `account_delete:<user>` (nothing is paid out: Dyce Cash is virtual); then frees the phone number (`phone_hash` replaced), renames the profile to `deleted_<hash>` / "Deleted player", blanks avatar, city, birth year, and deletes sessions, push tokens, contact links, friendships, blocks, notifications and their preferences, search and contact counters, quick-match tickets, XP, streak and badges. `users.disabled_at` is set, so nothing can sign in as them. Their games, ledger entries and reports stay (the ledger must outlive the user; opponents keep their history). **Messages they sent stay for the people they sent them to** (the design says so), which is a point for legal review (BACKLOG).
- **Export** (`GET /me/export`, 3 an hour): one JSON document of the caller's own data (profile, balance and wallet transactions, matches with opponents by username, friends and blocked by username, reports filed, disputes, badges, streak, messages they sent) and never a phone number or hash or anyone else's ids.
- **Space exit.** `GET /spaces/:id` for someone who used to sit there now returns the space with `seated: false`, no members and no match, plus `exit: { reason: 'host_closed' | 'expired' | 'removed' | 'left', hostName, refundedKobo }` (the match status tells a host close from a timeout) instead of `space_not_found`; a stranger still gets `space_not_found`. A `space_full` refusal carries `{ name, gameName, gameSlug, seats }` for the "space is full" screen. The three Space edge-state screens are driven by these.
- **Migration housekeeping.** New SQL functions are executable by PUBLIC unless revoked (0006 only covered the ones that existed): 0023 revokes and grants explicitly, and the test checks that `resolve_dispute` and the view are refused to the API role.

Needs a human (money and law, not guessed here): (1) **A dispute that is upheld for the disputer**: `reverse_txn` of the settle transaction needs the winner's balance to still cover it. Options: cap the correction at what they still have and record a shortfall, or post an `adjust` from `system_adjust` (creates Dyce Cash, which is virtual but must be a decision), or accept only disputes while the winner still has the pot. Until decided, `reversed` is applied only by hand. (2) **Holding a payout during review** is not built (no anti-cheat flag, no escrow after settle); the SPEC allows it only for flagged results. (3) **Message bodies** a deleted person sent stay with the recipients; NDPA erasure may require otherwise. (4) During the 30 days the profile stays visible; hiding it needs a rule for chats and games in progress. Owner: trust-safety-compliance
Consequences: a deleted person can never be signed into again (their number can start a new account); a Pool game cancelled by one player's deletion returns both stakes, and the opponent's card catches up the next time the match is read (no push yet). Two accounts of the disputing kind are rate limited per person, not per pair, so collusion checks remain in BACKLOG.

## ADR-035 · Board game engines: Chess, Checkers, Ayo/Mancala, Dots & Boxes, Ludo, Sea Battle · 2026-11-21

Context: Phase 4 adds six turn-based board games (GAMES #8-13) as pure engines in `packages/games/src/{chess,checkers,ayo,dotsandboxes,ludo,seabattle}`, run by the async match service (Ludo also live with 3-4 seats).
Decision, common to all: `players[0]` moves first (White, the bottom side in Checkers, the first pit row in Ayo, first roll in Ludo); a player may send `{ kind: 'resign' }` at any time, which the contract has no other way to express (the opponent wins; in Ludo the leaver ranks last); `validate` answers with a code (`not_your_turn`, `illegal_move`, ...) and never throws; the last move's animation data is kept in `state.last` and shown by `view()`; async `timers.turnMs` is a day (nothing enforces it yet).
- **Chess: our own engine, no dependency.** chess.js (BSD-2) would have been licence-safe, but its position is a mutable class that is rebuilt from a FEN plus a move list to know repetitions, it adds a runtime dependency to a package that Metro consumes as source, and its move order is not guaranteed across versions, which the cross-runtime determinism check cares about. A generator is a few hundred lines and is **proven by perft** on the six standard positions (start to depth 4 = 197,281; Kiwipete and positions 3, 4, 5 and 6 to depth 2-4; every count matches the published numbers) plus an Opera Game replay, castling / en passant / promotion / pin cases and SAN with disambiguation. State is JSON: the board as 64 characters in FEN order, castling and en passant as FEN fields, the move list in SAN, repetition counts. Actions are `{ kind: 'move', from, to, promotion? }` in algebraic squares; a pawn reaching the last rank without `promotion` is `promotion_required`. **Draws are automatic**, so no claim step exists in an async chat game: stalemate; insufficient material (bare kings, a lone knight or bishop, or only bishops on one colour of square; K+B v K+N and two knights are not drawn); the third occurrence of a position (same side to move, castling rights, and en passant only if a capture is really possible); 50 moves = 100 plies with no pawn move or capture. Checkmate wins over those. There are no draw offers (backlog). `cfg.fen` starts from another position.
- **Checkers: 8x8 English draughts.** 12 men each on the dark squares; men move and capture forwards, kings both ways; **capture is forced** and a jump must continue as far as it can, but the **longest capture is not required** (English rule); a man crowned mid-capture stops there; captured men leave the board when the move ends. A move is a path of squares `[from, to1, to2...]`, so a multi-jump is one action. You lose when you have no legal move; draw by 40 moves each (80 plies) without a capture or man move, or by the third occurrence of a position. Error codes `must_capture` and `incomplete_jump` tell the UI why.
- **Ayo / Mancala: one engine, `cfg.variant`.** Twelve pits in a ring (0-5 the first player's row, 6-11 the second's, pit `i` faces `11 - i`), 4 seeds each (`cfg.seeds` 3-6), sown counter-clockwise, action `{ kind: 'sow', pit }` with an absolute pit index. **Ayo Olopon (default):** lift a pit and sow one per pit, skipping the pit sown from; a last seed that lands in an occupied pit continues with that pit (relay, capped at 200 laps so a cycle cannot hang a room); a last seed in an *empty pit on your own side captures the seeds opposite* (only those; the landing seed stays), in an empty pit on the opponent's side nothing happens; first to 25 wins; if the player to move has no seeds the game ends and each side keeps the seeds on its own row; a 400-ply cap (`cfg.maxPlies`) scores the same way. Ayo is played with local differences, so these three choices (relay on an occupied landing pit, own-side-only captures, 25 to win) are to be confirmed with the product owner (backlog). **Mancala = Kalah(6, n):** stores, one seed in your own store as you pass it, the opponent's store skipped, the lifted pit not skipped, last seed in your store = extra turn, last seed in an empty pit of yours captures the opposite pit plus that seed, the game ends when one side is empty (the other side's seeds go to its owner) or at 25.
- **Dots & Boxes:** 5x5 dots (4x4 boxes; `cfg.dots` 3-8). Action `{ kind: 'line', dir: 'h' | 'v', r, c }`; closing a box claims it and **gives another move** (one line can close two boxes); most boxes wins, equal is a draw.
- **Ludo, 2-4 players.** The die is rolled inside the engine from the match RNG (`{ kind: 'roll' }`), so no client can choose it; then `{ kind: 'move', token }` for one of the movable tokens (a roll nothing can use passes by itself). Ring of 52 squares; seats start at 0 and 26 (2 players) or 0, 13, 26, 39; each token walks 51 ring squares (progress 0-50), then a private 5-square home column (51-55) and home (56) by exact count. A six leaves the yard onto your start square; **a six gives another roll after the move, a third six in a row passes the turn unmoved**; landing on opponents on a non-safe square sends **all** of them to the yard; the safe squares are the four starts and the four stars (8, 21, 34, 47), shared; your own tokens stack and there are **no blocks**. First to bring every token home wins; `cfg.rankAll` plays on to rank everyone, otherwise the rest are ranked by progress (ties share a place); `cfg.tokens` (1-4) makes shorter games. `ludoAutoAction` is the policy for a timeout or a bot. The RNG state never leaves `view()`.
- **Sea Battle:** 10x10, fleet 5-4-3-3-2 (carrier, battleship, cruiser, submarine, destroyer), ships may touch but not overlap. **Both players place at once** with one action (`{ kind: 'place', ships: [{ r, c, dir }] }` in fleet order; `seaBattleRandomPlacement(rngState)` is a client helper, not engine code), then take turns; the seed picks who fires first. One shot per turn and a hit gives no extra shot; `cfg.salvo` makes it one shot per ship afloat, fired together in `{ kind: 'fire', shots }`. `view()` returns, per board, the shots fired at it (hit, miss, sunk), the ships already sunk (public) and `ships` only to the owner, and to everyone once the game is over; before the battle a player only learns that the other has placed.
Consequences: all six export from `@dyce/games` with `actionSchema`s; the platform needs a `games` row and a registry entry per game (slugs `chess`, `checkers`, `ayo`, `dots-and-boxes`, `ludo`, `sea-battle`); `cfg` for Ayo is `{}` or `{ variant: 'kalah' }`, so Ayo and Mancala are either two catalogue entries or a mode choice at creation. Sea Battle is the only game with two simultaneous actors, so, like Word Hunt, `match.currentTurn` is only the first player yet to place and the app must decide whose move it is from its own `view()`. Ludo for 3-4 players in a Space needs the room to use `ludoAutoAction` on a turn timeout. Changing any rule, or the move order of a generator, changes results for the same seed: the determinism scenarios (`chess`, `checkers`, `ayo`, `kalah`, `dotsandboxes`, `ludo`, `seabattle`, `seasalvo`) pin them. Draws refund both stakes in Pool; Pool minimums are in GAMES.md. Owner: game-rules-engineer

## ADR-034 · Sports engines: 8 Ball, Darts, Basketball, Archery, and the shared angle helper · 2026-11-21

Context: Phase 4 sports games (GAMES #2-#5) are 2-player async, 3D in the app, and their outcomes must be decided by the server from quantised input and replay bit-for-bit on server, Hermes and Deno (ARCHITECTURE §6). `Math.sin/cos/atan2` are not bit-identical across those runtimes.
Decision: (`packages/games/src/{eightball,darts,basketball,archery}`, slugs `eight-ball`, `darts`, `basketball`, `archery`.) **Shared helper:** `physics/angles.ts` has `sinCosCenti(angle)`: the angle is an integer number of centidegrees, reduced with integer maths and a Taylor series using only + − × ÷ (error under 1e-15); everything else follows Cup Pong's rules (fixed timestep, only + − × ÷ and sqrt, no Date/Math.random). Cup Pong is untouched. Every action carries integers only and the zod schema bounds them; `view()` hides the RNG state (Archery also hides the winds of ends not yet reached). Each engine uses a constant number of RNG draws per action so replays stay aligned. All four are in the determinism scenario (`determinism/sports.ts`; the hashes include full animation traces for Basketball and 8 Ball).
**8 Ball:** table 2240 x 1120 mm, balls 57 mm, positions are integer 0.1 mm; the sim runs at 1/480 s (four sub-steps of the 1/120 s tick, so a 5 m/s ball never tunnels), finds ball-ball contact exactly (solve for the touching instant, apply the impulse there, move on), cushions reflect with restitution 0.72, pockets capture a ball whose centre comes within 70 mm (corner) or 58 mm (side) of the pocket centre, constant rolling deceleration, everything at rest after at most 15 s. Input `{angle (centidegrees 0-35999), power 0-1000, spinX/spinY ±100 inside a circle of 100}`, plus `place` (ball in hand) and `call` (the 8's pocket). **Spin is simplified, not a rolling-ball model:** top/back spin kicks the cue ball along its pre-contact heading by `0.55 × spin × approach speed` at its first ball contact (follow rolls on, draw comes back) then fades; side spin kicks it along the cushion on its next rail contact (0.35 × spin × impact speed) then halves. No squirt, throw or jump shots. **Rules:** random rack from the seed (8 centre, one solid and one stripe in the back corners); the breaker places the cue anywhere behind the head string; the table is open until a shot after the break legally pockets balls of one group only (mixed keeps it open; the break never assigns); you keep the table while you legally pocket one of your balls (any ball when open). Fouls: scratch, no ball touched, wrong first contact (the 8 only once your group is down; on an open table anything but the 8), contact but nothing pocketed and no cushion reached afterwards, and a break that pockets nothing and sends fewer than four object balls to a cushion. After a foul the opponent has ball in hand anywhere (a scratched cue returns to the head spot or the nearest free spot, and may be moved with `place`); balls pocketed by a foul stay down. Only the 8's pocket is called, and only when the shooter is on the 8 (without `call` the move is rejected as `call_required`); it wins if legal and the pocket matches, and loses if early, in another pocket, or with any foul (a scratch included). The 8 on the break re-racks (same breaker, unless they scratched too). `maxShots` (default 120) ends the game: fewer own balls left wins, an open table or equal is a draw. Left out on purpose: "choose to re-break", the three-foul rule, push-out and jump shots.
**Darts:** board in integer 0.1 mm (regulation ring radii), sector order clockwise from the top, sector edges from `sinCosCenti`, ring tests on squared integer distances. Input is the aim point `{x, y}` (0.1 mm, ±250 mm); the hand wobble is the sum of three uniform draws per axis (sigma 6 mm by default, `cfg.wobble` 0-200 for tests and difficulty), six draws a dart. 501 double-out with bust (below 0, leaving 1, or 0 without a double/bull's eye restores the score from the turn start and ends the turn); the bull's eye counts as a double, the outer bull is 25. "Around the clock": 1 to 20, then either bull; any ring of the number counts and a hit gives no extra darts. Three darts a turn; **equal turns** as in Cup Pong (if the first player finishes the second still throws that round; both finished → fewer darts wins, equal → draw); `maxRounds` (default 20) then fewer points left / fewer targets left wins, equal draws.
**Basketball:** five racks of five shots, one rack a turn (player 0 then player 1 on the same rack), racks fixed around a 6.7 m arc (literals in mm). A make is 1 point; **the last rack is the money-ball rack, every ball worth 2** (our reading of "moneyball last rack"), so a full card is 30. Input `{aim ±500, power 0-1000}` like Cup Pong (aim is a slope off the line to the hoop, elevation fixed at 52°); the server adds a release wobble (aim ±60, power ±20, two draws) and simulates the ball against the rim (a sphere against a ring), the backboard and the net crossing at 1/120 s. A centred input goes in about 50-70 % of the time under the wobble. Most points wins; equal is a draw (no sudden death).
**Archery:** 3 ends of 3 arrows (configurable), target 30 m away, 800 mm face, ten 40 mm rings, the inner 20 mm is an X (tie-break). Input `{aimX, aimY (mm on the face), draw 0-1000}`; the sight is calibrated for a full draw in still air, so a short draw drops short and drifts more, and a cross-wind of up to ±8 m/s (drawn once per end, the same for both archers, shown only from that end on) pushes a full-draw arrow up to about 25 cm. Tremor at release (four draws, 6 mm at full draw up to 26 mm at none). The first shooter alternates each end. Most points wins, then most Xs, then a draw.
Consequences: changing any constant changes results for the same seed, so a live match must be re-versioned. Positions are integers, so states stay small and JSON-stable; 8 Ball keeps the pre-shot table in `last.from` so the opponent's app can replay a shot with `simulateShot(..., true)`. Not yet run in Deno or Hermes: the only guard so far is Node plus the scenario hashes (FMA contraction on ARM Hermes is the thing to watch, as for Cup Pong). Turn-clock hints: 60 s (90 s for 8 Ball); the engines have no clock. Owner: game-rules-engineer

## ADR-033 · Tanks engine: heightmap ground, wind, three weapons, series trig · 2026-11-21

Context: Tanks (GAMES #7) is a 2-player async artillery game with destructible, seeded terrain, angle + power + weapon and wind. The physics must replay bit-for-bit on server, Hermes and Deno, and `Math.sin/cos` do not.
Decision: (`packages/games/src/tanks`) The world is 800 x 500 units; the ground is a **heightmap** of 200 integer columns (4 units each) built from 9 seeded control heights (90-260) joined with smoothstep, with a flat 11-column pad under each tank (columns 25 and 175). A blast carves the columns it covers down to the bottom of its circle (no caves or overhangs), then tanks settle onto the ground (they never move). Input is `{angle 0-180 whole degrees (0 right, 90 up, 180 left), power 1-100, weapon}`. Direction comes from a **Taylor-series sin/cos table for whole degrees** (`detmath.ts`, only + - x /, so IEEE-exact everywhere), never `Math.sin`. The shell flies at 1/120 s, semi-implicit Euler, gravity 100, speed 3 x power, sideways wind acceleration 1.2 x wind where **wind is an integer -10..10 drawn from the seeded RNG each turn and public** (the shooter sees it before firing). Hit points 100 each; a shell explodes on ground or on entering a tank (radius 12) and damage `floor(max x (R + 12 - d) / (R + 12))` falls to 0 at the blast's reach; your own shells hurt you. Weapons: `shell` (radius 24, 40 dmg, unlimited), `heavy` (40, 70, 2 each), `triple` (3 shells at angle -4/0/+4, radius 20, 30 dmg each, 2 each), resolved one after another so each crater changes the next flight. First tank at 0 hp loses; both at 0 from one shot is a draw; after `maxShots` (12) each the higher hp wins, equal is a draw. No jitter. Only the RNG is hidden; `view` is the state minus `rng`, and `last` carries the shot's impacts so a renderer can animate it (or re-run `simulateTanksShot` on the previous state for a full trace).
Consequences: changing a constant, the terrain generator or the trig table changes results for the same seed, so a live match must be re-versioned. Turn time hint is 60 s; the engine has no clock, the match service turns a timeout into a minimum-power shell (or forfeits after repeated misses). The game is Free-only until Pool is cleared for it.

## ADR-032 · Mini Golf engine: whole-hole turns, hidden putts, mirrored holes · 2026-11-21

Context: Mini Golf (GAMES #6) is 2-4 players, 9 holes top-down, stroke play, at most 6 strokes a hole, with deterministic fixed-timestep physics. It is played from a chat card, so waiting for an opponent between every stroke would make a hole take a day.
Decision: (`packages/games/src/minigolf`) **A turn is a player's whole hole**: they keep putting until they hole out or play a 6th stroke (a missed 6th scores 6), then the next player in seat order plays the same hole; when all are done the next hole starts and seat 0 goes first. Balls never collide, so order changes nothing about the physics. The nine holes are hand-made (400 x 800 cm, tee near the bottom, cup near the top; walls at least 12 cm thick so a 6 m/s ball never skips one; round bumpers; sand) and the seed decides which are **mirrored left-to-right**. Input is `{dx, dy, power 1-1000}` integers; the direction is the vector normalised with `sqrt` (no angle functions). Physics at 1/120 s: friction as a constant deceleration (90 cm/s² on grass, 420 in sand), restitution 0.78 on walls and 0.92 on bumpers, ball radius 2.1, cup radius 5.4, and the ball drops if it is over the cup slower than 240 cm/s (faster it rolls across). Ball positions in the state are integer millimetres. There is **no jitter**, so the same putt from the same spot always does the same thing; to stop a second player copying a first player's hole-in-one, **`view` shows you only your own putts on the current hole until you have finished it yourself** (counts and results of finished players are public; everything is public once the hole is closed). Fewest total strokes wins; equal totals share a placement. A beam-search test proves every hole is holeable in 5 strokes or fewer.
Consequences: the course, constants and mirroring are part of the rules, so changing them re-versions live matches. Turn time hint 60 s per stroke; a timeout should become a minimum-power putt toward the cup (the match service's `screenAction`). Free-only until Pool is cleared.

## ADR-031 · Word Tiles engine: our board, values and dictionary hook · 2026-11-21

Context: Word Tiles (GAMES #14; never "Scrabble") is a 2-4 player word-placement game with our own premium layout and letter values and a server-side dictionary check.
Decision: (`packages/games/src/wordtiles`) 15 x 15 board, rack of 7, a bag of **102 tiles (100 letters, 2 blanks)**: E12 A9 I9 O8 N6 R6 T6 S5 L4 U4 D4 G3 M3 C3 B2 P2 H2 F2 W2 Y2 V1 K1 J1 X1 Z1 Q1. **Values:** 1 = E A I O N R T S L U; 2 = D G M C; 3 = B P H F Y W; 4 = V K; 6 = J X; 8 = Z Q; blank 0. **Premium squares** are one octant mirrored eight ways (8 triple-word at (0,3), 13 double-word incl. the four corners and the centre star, 12 triple-letter, 20 double-letter) and are generated from a short list in code. Scoring: premiums count only under tiles placed this turn, every word the play makes (main + cross words) is scored separately, **bingo (all 7 tiles) adds 30**. Moves: `play` (tiles in one row or column, gaps allowed only where board tiles fill them, joined to the board, first play covers the star with 2+ tiles), `exchange` (only while the bag holds at least 7 tiles; returns tiles are reshuffled into the bag with the seeded RNG), `pass`. **No challenges:** the server refuses a play with a non-dictionary word (`invalid_word`) and it costs nothing. The game ends when a player goes out with the bag empty (they gain every other rack's value, each opponent loses their own) or after every player has made two scoreless turns in a row (all lose their own rack value); highest score wins, equal is a draw. **The dictionary is injected:** `createWordTilesEngine(wordSet)`, with `wordSet = { id, size, has(UPPER) }` (`makeWordSet`), and the id is stored in `state.dict`; the pure `wordTilesAnalysePlay(board, rack, tiles, wordSet)` is the dictionary-aware rules function the client can call for a score preview. The in-repo list is the Word Hunt list plus a few two-letter words (about 5 500 words, 2-10 letters, original work, no licence to carry; see `words.ts`). `view` shows only your own rack (everyone's once the game is over), the bag **count**, and never the bag order or the RNG; a move record says how many tiles were exchanged, not which.
Consequences: the small list will refuse some valid words and long words are rare, so a larger list (for example the public-domain ENABLE list, licence permitting) should be loaded by the server before Pool is switched on: register a second engine entry built with `makeWordSet(bigList, 'enable-1')`, keep the old id registered while matches using it are live, and only new matches take the new id (the word set is never part of the state, so hashes do not depend on it, but whether a play is legal does). The engine has no clock; a turn that times out should become `{kind:'pass'}` (match service), and repeated timeouts are a forfeit decided by the platform. Free-only until the bigger list is in.

## ADR-030 · Filler engine · 2026-11-21

Context: Filler (GAMES #17) is a 2-player colour-claiming game on an 8 x 7 seeded grid where the majority wins.
Decision: (`packages/games/src/filler`) Six colours. The seeded grid has **no two touching cells of one colour** and different start colours. players[0] starts in the bottom-left corner, players[1] in the top-right. A turn is `{kind:'pick', colour}`: your whole region takes that colour and swallows every free cell of it that touches the region, chaining through free cells of that colour. You may not pick your own colour or the colour your opponent currently holds (so a legal colour always exists: at least four). ## ADR-029 · Anagrams engine · 2026-11-21

Context: Anagrams (GAMES #16) gives every player the same six letters and 60 seconds, played on their own time like Word Hunt.
Decision: (`packages/games/src/anagrams`) The six letters are a **seeded shuffle of a 6-letter dictionary word** (never handed over already spelled), so a full-length anagram always exists. Words need 3-6 letters, must be in the dictionary and spellable from the letters (each used at most as often as it appears); duplicates count once and bad words are dropped and counted in `rejected`. Highest score wins, equal is a draw, 2-8 players. The dictionary is the Word Hunt list (`dyce-v1`), injected through `createAnagramsEngine(words, id)` and stored in `state.dict`; a larger list is loaded exactly as for Word Hunt (keep old ids registered for live matches).

## ADR-025 · Party rooms, Crazy Cards in the card room, and quick match · 2026-11-20

Context: ADR-023 built the engines for Crazy Cards, Imposter, Werewolf, Charades and Doodle Guess; ADR-022 built Spaces and a room for Whot!. This connects them, and adds quick match (SPEC §7). The wire protocol for the screens is `docs/PARTY_ROOM_PROTOCOL.md`. Migration 0019.
Decision:

- **Two kinds of room in one registry.** `LIVE_GAMES` is now a union: `turns` (Whot!, Crazy Cards: one player acts, a turn clock, the room plays for a seat that timed out or left) and `party` (Imposter, Werewolf, Charades, Doodle Guess: phases and timers, many act at once). The registry also carries what the lobby needs so the API and the app cannot drift: seat range, the Pool payout schemes allowed, per-game `options` (checked at create, `invalid_options`), `quickMatch`. **Crazy Cards runs in the existing turn room unchanged** (a registry entry, a `games` row, 2 to 4 seats like Whot!); the GAMES.md range of 6 waits for the 3D table.
- **`PartyMatch`** (`apps/game-server/src/party-match.ts`) is to party games what `LiveMatch` is to turn games: a plain class with no network or clock, tested with a fake scheduler. The room (`room.ts`) picks one by the registry and stays glue. Final ranking is one shared function (`outcome.ts`), so a forfeit, a draw and "everyone left" mean the same in both.
- **Time is the room's.** Every second (`tickMs`) the room feeds the engine `{ kind: 'tick', ms }` as `ROOM_ACTOR` for the real time that passed (sliced to the engine's 10 s maximum). A seat can never send one (schema level and the engine's `room_only`). **The clocks stay stopped until every seat has connected once**; seats that never show up forfeit after the join grace and the game starts without them (the same after a restart). When the clock is only waiting for seats that have forfeited (a drawer who left) it runs forward in 250 ms steps (`blockers` per game) instead of making the table wait.
- **What a seat is sent.** Its own `engine.view()` inside `LiveState`, only when something it can see changed (a countdown is not a change: the client counts down from `turnDeadlineAt` and `serverNow`). That is also a privacy rule: a Werewolf villager is not sent a message when a wolf acts. Party rooms never send `turnUserId` (it would reveal who holds a night role); `canAct` says only whether *you* may act. Streams (Doodle strokes) are coalesced to one broadcast per 150 ms.
- **Persistence.** Every player action is a `match_moves` row and the new state is saved with it in one transaction **before** anyone is told (a failed save refuses the move and changes nothing). A tick is saved only if it changed something (a phase ended, a silent seat was filled in) and has no player (`match_moves.user_id` is nullable for `tick` rows, constraint in 0019); a tick that only moved a clock is not saved. Strokes are batched into one transaction every 1.5 s (a crash loses at most that much of a drawing, never a vote). After a restart a room resumes from the last saved state with the clock of that moment.
- **The canvas is a stream, not part of the state.** The first soak run (below) showed every stroke re-sending the whole drawing to everyone: 24 KB per client per second and 32 ms CPU per room-second. The view now carries only `strokeCount`; the drawing travels in `canvas` messages that are the difference from what that seat last got (`diffCanvas` / `applyCanvas` in `@dyce/games`, a reset on join, a new turn, undo and clear). A game can declare a `stream` (split and diff) in the registry.
- **Leaving.** As ADR-022 for every room: leave or 60 s offline forfeits, ranks last, takes no money; one left wins at once; everyone gone refunds. A party game's timers fill in what a forfeited seat would have done. No bot replacement.
- **Table talk** (party rooms): `chat` messages, 200 characters, profanity refused, one line per 600 ms, kept in memory (the last 60, replayed on join to those who could hear them). Who hears what is per game and phase (`chatAudienceFor`): Imposter only while voting and after; Werewolf wolves-only at night, the living by day, the dead talk to the dead and hear everyone, as ADR-023 asked; Charades everyone but the actor; Doodle none (a guess is a move). Not stored, not moderated beyond the word list; reports and chat moderation stay with trust and safety.
- **Spectators:** only a dead Werewolf player, who is still a seated player whose view shows every role. Nothing in the designs offers watching a game you are not in, so the room does not accept outsiders.
- **Pool for party games.** Imposter and Werewolf pay the winning side equally, so a Space for them accepts only `winner_all` (`invalid_payout` otherwise); a loser sharing a 50/30/20 slot made no sense. Charades and Doodle accept any scheme (placements from team scores / points), a Werewolf with no winner after 10 nights and a level Charades are draws and refund every stake. Seats go up to 12 (the create schema allowed 8).
- **Quick match.** A ticket table (`quick_match_tickets`) and `QuickMatchService`. Join (a game with `quickMatch`, Free or a Pool stake) → pairing runs in one transaction that locks both tickets with `FOR UPDATE SKIP LOCKED` (parallel joins and sweeps never pair a ticket twice; a missed pair is found by the next 2 s sweep). Pairing rules, all config: same game, mode and stake; level within 3 until either has waited 15 s, then anyone; **never a blocked pair, never a disabled account, never the same two people within 10 minutes**; one open search per person. Pairing opens a hidden two-seat `quick_match` Space (no code lookup, not in "your spaces" until live) and **escrows both Pool seat fees at that moment** with `stake_pool`; a seat whose stake is refused (cash, 18+, limits, too many spaces) drops only its own ticket (`failed`) and the other goes on to the next candidate. Both have 10 s (+3 s grace) to accept; a decline or a missed window closes the space and `refund_match` returns both stakes; the one who did not walk away is back in the queue with their place. Both accepting starts the match through `SpacesService`, so everything after is an ordinary live Space. A crash between accept and start is repaired by the sweep. Limits: 30 searches an hour, three skipped or missed matches in 10 minutes means a wait (`quick_match_cooldown`), IP throttles on the routes. **Strangers get no chat:** nothing here creates a conversation or a friendship; the opponent card shows name, avatar, level and win rate only; a later message goes to Requests by the existing rules (ADR-010; tested). Games: Whot! and Crazy Cards (1 v 1 live). Async games (Cup Pong, Word Hunt) against strangers would need a chat card, which strangers must not get: BACKLOG. The `quick_match` realtime event carries the ticket; the app also polls while searching.
- **Money.** No new money path: stake, unstake, settle and refund are the existing SQL functions, called by `SpacesService`, `QuickMatchService` and `PgLiveMatchStore.finish`. `ledger_check_invariants` is empty after every integration test and after the real-process run.
- **Measured** (`party-soak.test.ts`, 20 Doodle rooms x 8 seats, a drawer streaming 6 actions a second, simulated time): 6 to 8 ms CPU per room-second (so one core holds more than 100 such rooms before the network matters; the figure includes serialising every message), 2.5 KB per client per second, 0.5 database writes per room-second. Before the canvas stream: 24 KB, 32 ms. Network and database latency are not in these numbers.
  Consequences: the app gets `SpaceView.options` / `quickMatch`, `LiveState` gains `roomKind`, `canAct`, `waiting`, and new routes `/quick-match`. New config keys `quick_match_*` (8). New error codes `invalid_options`, `quick_match_unavailable | active | not_found | expired | rate_limited | cooldown`. `apps/game-server/scripts/live-e2e.mjs` (`pnpm -F @dyce/game-server e2e`) runs the built API and game server as real processes. Not built: public Spaces, lobby chat, bots, spectating outsiders, Redis for more than one game-server process, push for "match found", async quick match. Owner: realtime-spaces-engineer

## ADR-024 · Phase 3 social layer: search, profiles, leaderboards, notifications, push, XP · 2026-11-20

Context: SPEC §10-12 and the ADR-015 follow-ups. The social layer needs events from many writers (the async match service, the Colyseus game server, the wallet functions, friends, spaces), so each service remembering to emit them would drift.
Decision:

- **Progress and notifications are written by the database** (migration 0018), in the transaction that causes them. Triggers on `matches` (finished: XP, level, streak, badges, then results), `match_players` (an invite), `friendships`, `spaces`, `payment_requests` and `ledger_txns` call one helper, `_notify`, which skips yourself, disabled accounts, anyone blocked either way, and (for money requests) non-friends. `xp_events`, `streaks`, `user_badges` and `badges` are no longer writable by the API role. A failed transaction produces nothing.

Badges: First Win, 10 Streak (10 days in a row), Pool Shark (5 Pool wins), Space Host (a finished Space of 4+), Whot Master (10 Whot! wins). Doodle Artist waits for Doodle Guess.
- **Notifications** are rows in `notifications` (kind, actor, payload, dedupe key). A kind with a dedupe key ("your turn" in one match) is one row, refreshed and unread again on each new turn, so a long game is one line. Stale reminders are marked read when the turn moves, the match ends or the invite is answered. Text and destination come from one pure function, `describeNotification`, shared by push and the list. Rows from someone you later block are hidden and not counted.
- **Push.** The queue is `notifications.dispatched_at IS NULL`. `PushDispatcher` (every 3 s, `FOR UPDATE SKIP LOCKED`) skips kinds that are never pushed (Free results, level-ups, badges), rows older than 6 h, a switched-off group, **quiet hours (skipped, not delayed)** and people without a device; otherwise it sends through a `PushDriver`: `console` in development, `ExpoPushDriver` (Expo Push API, chunks of 100) in production (`PUSH_DRIVER=expo` is required there). Dead tokens (`DeviceNotRegistered`) are deleted; a failed send retries up to 3 times. A token belongs to one person at a time (signing in as someone else on the phone moves it); at most 10 devices each. Each handled row also sends a realtime `notification` event so the open app refreshes its list and bell.
- **Preferences.** `notification_prefs`: five switches (turns, invites, pool, money, spaces; missing = on), quiet hours as minutes after midnight with the phone's UTC offset. They govern push only; the list always shows everything.
- **Search** (`GET /search/people`). Friends, contacts and people you chat or play with match on @username prefix or any word of their name from 2 characters. **Strangers match only on the start of a @username, from 3 characters**, so the endpoint cannot browse people by name (ADR-008's exact-match stance, loosened as far as the SPEC's "by @username" needs). 15 results, blocked and disabled never appear, only public fields, `people_searches_per_day` (600) per person plus the IP throttle. Games, your spaces, chats and transactions are filtered on the phone from what is loaded; a Space code is looked up exactly; recent searches stay on the phone.
- **Profiles** (`GET /users/:username/profile`). Blocked either way, disabled or unknown all answer `user_not_found`. A stranger shows level, badges, win record, mutual friends and head to head (your own results against them) but **not** recent games; money (Pool net, best pot, what a game paid) is only ever your own. No phone number or hash is selected anywhere (tested). `canRequest` follows their "who can add me" setting.
- **Leaderboards** (`GET /leaderboards`): the Lagos week (Monday 00:00), Friends (you and your friends, friends with 0 listed) or Everyone (only people with XP), optionally one game, XP or Pool net winnings. **Pool winnings are ranked among friends only** (money). Computed live from `xp_events` and finished matches; the old `leaderboard_weekly` view is unused (UTC weeks, no game filter).
  Consequences: the app's "Lagos / Nigeria" board scopes in the design are not built (the SPEC says friends and global); no opt-out from the global board yet (BACKLOG). Real push delivery was never exercised against Expo. Owner: social-discovery-engineer

## ADR-023 · Phase 3 rules engines: Crazy Cards, Doodle Guess, Imposter, Werewolf, Charades · 2026-11-20

Context: the party and card games need pure engines (`packages/games/src/{crazycards,doodleguess,imposter,werewolf,charades}`) before the party room and renderers exist. Slugs `crazy-cards`, `doodle-guess`, `imposter`, `werewolf`, `charades`; shared helpers in `src/party/` (`common.ts`, `words.ts`). The rules below were not in GAMES.md and are decided here.

- **Time is a room-only action.** Live games with phases take `{ kind: 'tick', ms }` (1 to 10,000 ms) with `by = ROOM_ACTOR` (`'$room'`, never a legal player id). The engine counts its own timers down and moves the phase on at zero (missing votes become abstentions, a silent speaker gets an empty clue, a drawer who does not choose gets the first word). The engine refuses a tick from any seat (`room_only`); the room must also drop `tick` from client messages (`isRoomOnlyAction`). Seeded words, roles and tie-breaks live in the state, so a replay of the same actions is identical.
- **Pool placements.** Imposter and Werewolf return two groups: the winning side shares first place, the other side second (`settle_match` splits the combined slots equally). Werewolf is a draw (one group, everyone refunded) if `maxNights` (10) pass with no winner. Doodle Guess and Charades rank by points; equal totals share a placement; all equal is a draw. Charades ranks team scores and gives each member the team's placement.
- **Crazy Cards.** 108 cards, 7 each, number-card starter, no stacking, Wild Draw Four legal at any time (no challenge), Reverse acts as Skip with 2 players, a drawn playable card may be played or passed, "last card" call required on the play that leaves one card (miss = draw 2), going out needs no call. One round: first out wins, others rank by points left (number = face, action 20, wild 50). Blocked (nobody can draw) ranks by points.
- **Imposter.** 1 imposter for up to 7 players, 2 from 8 (`imposters` overrides, never half the table). Phases `reveal` → `clue` (default 2 rounds, 1 to 3 words, profanity refused, no check against the secret so nothing leaks) → `vote` → `guess`. Each voter names exactly as many suspects as there are imposters; the top N are accused and a tie across the cut accuses only those above it. If the accused are exactly the imposters, each imposter gets one guess at the word (a correct one wins the round for the imposters), otherwise the imposters win. Imposters know each other; nobody sees the imposter list, and only crew see the word, until the end.
- **Werewolf.** 1 wolf for 5 to 6 players, 2 for 7 to 9, 3 for 10 to 12, plus one seer and one doctor. Night actions are final; the wolves' most-named victim dies (a tie is broken by the seeded RNG) unless the doctor named them (self allowed, repeats allowed). Day has `ready` to end discussion early; the vote is by strict plurality (ties and abstentions lynch nobody). A dead player's role becomes public and they spectate with every role visible, so the room must keep dead players out of the live chat. `currentPlayers` at night reveals who still holds a night role: the room must not broadcast it.
- **Charades.** 4+ players in 2 teams (up to 4 with `teams`); 3 players or `solo` means everyone plays for themselves (the guesser must be named and also scores). Each team gets rounds × biggest-team turns so uneven teams stay fair. A turn is `start` (or the ready timer forfeits it), then `got_it` / `skip` (3 skips) for up to 8 cards or 60 s. Mode `act` shows the card only to the actor; `headsup` shows it to everyone but the holder.
- **Doodle Guess.** 3 rounds, each player draws once per round, 3 words offered. A correct guess scores 50 + floor(150 × timeLeft / drawMs); the drawer earns half of each guesser's points. Up to a third of the letters (max 3) are revealed evenly over the clock, in a seeded order the view never exposes. A guess one edit from the word says "close" (the text is not shown). Strokes are actions with at most 64 integer points on a 0 to 1000 canvas; `cont` extends the last stroke so a long line streams in chunks; the canvas is capped at 300 strokes and 4,000 points per turn (`canvas_full`) so the state stays small (the room should still avoid writing the full state to Postgres on every stroke).
- **Words.** Packs (`general`, `food`, `animals`, `places`, `naija`; Charades `lagos-life`, `animals`, `jobs`, `actions`) are original, in-repo, and pass `isCleanText` (tested). An engine copies the words it needs into its state at `init`, so editing a pack never changes a running match; it does change what a seed deals, hence `WORD_PACKS_VERSION`.

Consequences: none of the five is registered in `LIVE_GAMES` or the `games` table yet (the party room needs a room that accepts simultaneous actors and ticks, and a migration for the rows). Crazy Cards is turn-based like Whot! and only needs the row and the registry entry (`crazyCardsAutoAction` is ready). No contract change was needed; `describeEngine` gained an optional `systemActions` for tick-driven phases.

## ADR-022 · Spaces and the live game server (Whot!) · 2026-11-19

Context: ARCHITECTURE §5 puts live games (Spaces) in Colyseus, with the room created by the API through a signed server-to-server call, the same engines as async matches, per-client `view()`, 60 s reconnection and settlement through `settle_match`. SPEC §7 describes the Spaces tab. This slice is private Spaces (friends or a code) and one live game, Whot! for 2 to 4 seats. Migration 0017.

- **A new app, `apps/game-server`** (`@dyce/game-server`): Colyseus 0.16 (`@colyseus/core` + `@colyseus/ws-transport`, no `@colyseus/schema`). We do not use Colyseus state sync: hidden information must reach each client only through the engine's `view()`, so the room sends each seat a `state` message holding its own `LiveState` (`packages/shared/src/schemas/spaces.ts`) after every change, and receives `move`, `leave` and `sync`. One room per match; **the room id is the match id**. It serves `GET /health` and the API's `POST /internal/rooms` on the same HTTP server as the Colyseus matchmaking and WebSocket routes.
- **Rules live in `LiveMatch`**, a plain class with no network or clock of its own (timers are injected), tested without Colyseus (16 tests). The room is only glue (auth, messages, broadcast). All state changes go through one queue so a move and a timeout can never interleave across an `await`. A move is checked against the action schema, the version the player saw (`stale_version`), whose turn it is and the engine's `validate`, then applied, **persisted in one transaction** (`match_moves` row + `matches.state`, guarded by `state_version = seq - 1`) and only then broadcast. Persisting every move (not batches) keeps a lost room recoverable and costs one small transaction per move.
- **The database is the source of truth, the room is a cache.** `ensureRoom(matchId)` builds a room from the match row (state, version, forfeits in `matches.live_meta`). If the game server restarts, the app's next `POST /spaces/:id/connect` makes the API ask again and the table comes back where it was (tested, and verified by restarting the server mid-game in a browser). Turn clocks restart at a full turn and seats get a join grace again.
- **Auth.** The app sends its access token when it joins (`joinById(roomId, { token })`); the room verifies it with the API's JWT secret (HS256, issuer and audience as `TokenService`) and checks the user holds a seat. A second connection from the same person replaces the first (close code 4010). The API's room call is signed `HMAC-SHA256(INTERNAL_SECRET, "<ms timestamp>.<body>")`, valid for a minute; each app keeps its own copy of the 20-line signing file. Env: API `GAME_SERVER_URL`, `GAME_SERVER_PUBLIC_URL`, `INTERNAL_SECRET`; game server `PORT`, `DATABASE_URL` (the same restricted `dyce_api` role), `JWT_SECRET`, `INTERNAL_SECRET`, `RECONNECT_SECONDS` (60), `JOIN_GRACE_SECONDS` (90).
- **Spaces in the database.** `spaces` and `space_members` already existed (0003). 0017 adds `space_members.join_n` (sitting down again pays again, so the stake idempotency key carries it), `matches.live_meta`, `spaces.started_at/ended_at`, the `whot` row in `games` (`sync = 'live'`, 2 to 4 seats, Pool allowed), config keys, and **`unstake_pool(match, user, idem)`**. A space owns one `matches` row from creation (status `invited` while waiting, `space_id` set). Each seat is a `match_players` row. In Pool the seat fee is escrowed with `stake_pool` **when the person sits down** and returned with `unstake_pool` when they leave or the host removes them, and `refund_match` returns everything when the space closes or goes stale (6 h, scheduled job), so the escrow always equals the money of the people seated. Starting initialises the engine, flips the match to `active` and sets `payout_scheme`; two players who picked 50/30/20 are paid 60/40 (50/30 of two would be 62.5/37.5). Every change to a space happens under a row lock on `spaces`.
- **Who may join.** Friends-only: friends of the host. Invite: anyone with the code. Blocks with any seated person refuse. A removed person cannot return. Public Spaces and quick match are not built.
- **Leaving and forfeit.** `leave` (the menu, confirmed in the app) or 60 s without a connection forfeits the seat, in Free and Pool alike (the ARCHITECTURE bot replacement for Free is not built). A forfeited seat finishes **last** (later forfeits place above earlier ones), never takes money, and is played with the game's own `autoAction` while it is still in the turn order; when one player is left that player wins at once. A seat that never connects within the join grace forfeits the same way. Nobody can leave a running game through the lobby (`space_live`). A seat that runs out its 25 s turn clock is played automatically whether or not it is connected.
- **Settlement.** `PgLiveMatchStore.finish` writes placements, calls `settle_match` once in the same transaction, restores `forfeit` results, closes the space and returns the rows the result screen shows. Failure is retried five times; if it still fails the match stays `active` and the next connection rebuilds the room and finishes it (recovery path tested at unit level). `ledger_check_invariants` is clean after every integration test and after the browser runs.
- **Realtime.** The lobby uses HTTP plus a new `space` event on the existing `/realtime` socket (each member gets their own view). The game server does not publish to that socket; the app moves from the table to the result screen on the final `state`, and refetches the space.

Consequences: one game-server process only (Colyseus `LocalPresence`/`LocalDriver`); scaling out needs Redis presence/driver and sticky routing, like the chat hub. No XP, streaks or badges for Spaces yet (the progression work owns them). Not built from the designs: lobby chat, "Invite friends" from the lobby (the code and share link exist), ready toggle (everyone sitting is ready), lock seats, spectators, the 3D table. Whot is capped at 4 seats here although the engine supports 6. Owner: realtime-spaces-engineer

## ADR-021 · SMS invites, the guest web game and joining up · 2026-11-19

Context: SPEC "Sending a game to a non-Dyce contact": a user texts a game to someone who is not on Dyce; the link opens a page where they can play with no account and, if they sign up, they land in that game against the person who invited them. `sms_invites` existed since 0002; migration 0016 adds what was missing.

- **The number is never stored.** `POST /invites` takes the number (E.164, or national with `country`), hashes it (`HMAC(PHONE_HASH_SALT, "phone:"+e164)`, the same hash as `users.phone_hash`), sends the text through the existing SMS driver and forgets it. Logs use `maskPhone`. A failed send deletes the row, so it uses nobody's limit.
- **Refused:** a bad number, your own number, a number already on Dyce (`already_on_dyce`: they are a contact to add, not to text), a game that is not enabled with an engine, the dev game. **Limits** (serialised with advisory locks, so parallel sends cannot slip past): `sms_invites_per_day` per sender per Lagos day (50), `sms_invites_per_number_per_day` per number from everyone, rolling 24 h (3, new config), and one text per sender and number per minute.
- **Token and link.** Token = 96 random bits as 16 URL-safe characters, expires after `invite_ttl_days` (7, new config). The SMS link is `<INVITE_BASE_URL>/i/<token>#p=<digits>`. The **fragment** carries the invited number back to the invitee's own browser or app so sign-up can be prefilled; a fragment is never sent to a server, so we still hold only the hash. The number is already in the sender's contacts and with the SMS provider; forwarding the link shows the invitee's number to whoever it is forwarded to (accepted). `GET /invites/:token` (public, per-IP throttled) returns the inviter's public profile, the game, whether it is guest-playable, the guest's score once finished and `state` open / expired / joined; it marks a fresh invite `opened`. It never contains a phone number.
- **Guest match.** `guest_runs` (one per invite). `POST /invites/:token/guest` creates a run for **Word Hunt** (`invites/guest-games.ts`; Cup Pong joins when its renderer lands) with a fresh seed and returns a secret guest token (256 bits, only its SHA-256 is stored, valid 1 hour). The server holds the engine state (players `guest` and `host`, so the inviter's id never reaches the browser) and the browser only renders `engine.view()`: grid hidden until `start`, moves validated with the engine and screened with the same `screenAction` clock rule as signed-in play (a late submit scores nothing), outcome decided on the server. **Reuse:** a run that has not started can be re-issued (a refresh) and the old token dies; once the grid has been shown only the token holder can continue (`guest_already_played` otherwise), so a link cannot be used to see boards repeatedly; a repeat of the final submit is acknowledged. A guest token only works on its own invite; invite expiry and `joined` close the game.
- **Joining up.** `POST /invites/claim` (signed in, called by the app right after the profile exists, safe to repeat) joins every live invite whose hash equals the account's: the pair become **friends** (accepted, requested by the inviter: the inviter chose to text this number and the invitee chose to sign up with it, so this is not a stranger), the direct chat opens, the invite becomes `joined`, and the game becomes a normal Free match with the invite's id as its id (`MatchesService.startFromInvite`, the only change in the match service). If the guest **finished** a round, their moves are replayed through the engine on the guest's seed: they keep their score and the inviter plays next. A round that was started but not sent is not carried over (the grid was seen): a fresh invite match is sent instead. Blocked pairs and disabled inviters are skipped; expired invites are not joined. The step is idempotent and recoverable (a crash after `joined` but before the match is finished by the next call). A token passed to `claim` only puts that invite first; it never joins someone with another number.
- **Errors:** `invite_not_found` 404, `invite_expired` 410, `invite_used` 410, `already_on_dyce` 409, `invite_rate_limited` / `invite_number_limited` / `invite_too_soon` 429, `guest_unauthorized` 401, `guest_already_played` 409, `guest_game_unavailable` 422.
- **Tests:** `db/tests/invites.test.ts` (34 tests, real PostgreSQL): hash only and link shape; refusals; per-sender, per-number, cooldown and parallel limits; failed SMS; the landing page; the guest round (hidden grid, server scoring, late submit, repeat submit, token holder only, re-issue, expiry of token and invite); join-up (friends, chat, card, score kept, inviter plays and wins the same grid, idempotent, crash retry, fresh match, wrong number, expired, blocked, several invites, profile required).
- **Not done (BACKLOG):** real SMS delivery is untested against Termii/Twilio (ADR-007); store link association; resend or revoke for a sent invite; a push "your friend joined"; the blue-bubble SMS thread in Chat.
  Consequences: `@dyce/shared` gains `schemas/invites.ts` and two config keys; `INVITE_BASE_URL` is a new env value (default https://dyce.games); browsers need `CORS_ORIGINS` to include the web build. Owner: growth-invites-engineer

## ADR-019 · Word Hunt on the match service · 2026-11-15

Context: first real game on the async match platform (ADR-016); engine rules are in ADR-017, the app side in the app's ADR-018.

- **Registry and catalogue.** One entry in `matches/engines.ts` (`word-hunt`, cfg `{ roundMs: 80000, minWords: 25 }`) and migration `0013_word_hunt.sql` (2D, async, 2 players, category `word`, **`supports_pool = false`** and enabled). Pool stays off for this game until settlement has been checked against a game where both players act at once; flipping it is a later migration.
- **The round clock is a server rule (`screenAction`).** Engines have no clock, so `EngineEntry` gets an optional `screenAction(ctx)` that sees the move, the mover's earlier moves (with their database timestamps) and `now`, and returns the action to apply. It is changed, not refused, on purpose: a refusal would leave the player stuck in `playing` and the match would never finish. The stored move is the action that was applied, so a match replays to the same state. The check is per player (each is measured from their own `start`), and the grace covers network time and the gap between the server recording `start` and the client seeing the reply.
- **Dictionary and grid** are checked by the engine (`apply` drops words that are not in the list or not traceable; duplicates count once). The server rule above is the only extra rule.
- **No turn order.** `current_turn` for Word Hunt is the first player (by seat) who has not finished, because both players act at once and the column holds one id. `submitMove` allows anyone in `currentPlayers`, so this is only a label; the app works out whose move it is from the player's own `view()`.
- **Slug pattern.** The create-match schema allowed only `[a-z0-9_]` and refused `word-hunt`; it now allows hyphens (`[a-z0-9_-]`), which every engine slug but Pig uses. Service tests call the service directly and missed it; the browser run found it, and `packages/shared/src/games.test.ts` now covers it.
- **Not covered yet:** a player who never starts, or starts and never submits, holds the match open (no timer or forfeit exists; the next platform slice). Changing the dictionary or letter weights changes boards for the same seed (ADR-017): version the match before doing that.

## ADR-018 · Pool mode for async matches · 2026-11-15

Context: ADR-016 shipped Free matches; the money layer (ADR-004/012: `stake_pool`, `settle_match`, `refund_match`, daily usage) already existed. This adds Pool on top, with no new way to move money from TypeScript.
Decision:

- **Stakes.** `POST /matches` takes `mode: 'pool'`, `stakeKobo` and `allowCounter`. The limits are config (`pool_min_stake_kobo` 10000 = ₦100, `pool_max_stake_kobo` 2000000 = ₦20,000; `invalid_stake` carries both). The creator's stake is escrowed by `stake_pool` in the same transaction that inserts the match, so a refused stake (`insufficient_funds`, `adult_required`, `pool_frozen`, `over_pool_stake_limit`, `over_pool_games_limit`) rolls everything back: no match, no card, no money moved. The invitee's stake is taken by `stake_pool` when they accept, in the transaction that starts the game. A game with `supports_pool = false` is refused (`pool_not_supported`); migration 0014 turns Pool on for the dev-only Pig row. Idempotency keys are `stake:<match>:<user>`, so a retry or a double tap stakes once; a retry that changes mode or game is `message_id_taken`.
- **Counter-offer (decided here; the design and SPEC §9 allow one).** Only the invitee, only on a plain invite, only once, only if the sender left `allowCounter` on, and only for a smaller stake (at least the minimum) or `0` = play it free: `POST /matches/:id/counter { stakeKobo }`. Status becomes `countered` and nothing moves yet; they must be an adult with enough cash for their own offer. The sender then accepts (`POST /matches/:id/accept`, the same endpoint) or declines. Accepting calls the new SQL function `restake_pool` (migration 0014: gives the difference back from escrow to the creator in one balanced transaction; taken to 0 it turns the match into a Free one) and `stake_pool` for the invitee at the counter amount, all in one transaction. If the invitee can no longer cover it, the whole step rolls back and the sender gets `opponent_cannot_stake` with the reason; the offer stays open. Either player can end a countered match (decline or withdraw) and every stake is refunded. The design's "Counter back" is not built (SPEC: once); neither is "Run it back" (BACKLOG). A counter starts a fresh 24h window for the sender.
- **Refunds.** Decline, cancel and expiry of a Pool invite (plain or countered) call `refund_match` ('cancelled' / 'expired'). Expiry happens when someone opens the match and also in a sweep (`MatchMaintenance`, every 5 minutes, `expireStaleInvites`), so locked cash is never stranded by an invite nobody reopens, including for a pair that has since blocked each other. Daily usage is not rolled back by a refund (the same as `refund_match` itself).
- **Settlement.** When the engine says the match is over, `submitMove` writes placements and calls `settle_match` in the same transaction: the winner takes the pot, a draw refunds both stakes. A repeated or concurrent final move pays once (the move log and the escrow state both guard it).
- **What clients see.** `MatchView` gains `potKobo`, `counterStakeKobo`, `allowCounter` and, per player, `stakedKobo` and `payoutKobo`; the chat card payload gains `stakeKobo`, `potKobo`, `counterStakeKobo`, `allowCounter`; the `match` event carries the view. `GET /games/pool` returns the limits, today's usage, the reset time and whether the age gate was answered, for the stake picker. The age gate stays `POST /profile/age-gate` (birth year only, ADR-007).
- **Tests.** `db/tests/pool-matches.test.ts` (31 tests on real PostgreSQL, `ledger_check_invariants` after every one): create and its refusals (limits, funds, 18+, daily stake and games limits, no-Pool game, non-friend, blocked), retry and double tap, accept and its refusals, decline / cancel / expiry (lazy and sweep) refunds, every counter path, settlement for a win and a draw, a retried final move, and the pool info.
  Consequences: `@dyce/shared` gains `counterMatchSchema`, `PoolInfo` and the fields above; the app consumes them. New error codes: `pool_not_supported`, `invalid_stake`, `counter_not_allowed`, `opponent_cannot_stake` (AuthError); `restake_pool` raises only codes already in `DYCE_ERROR_CODES`. Owner: game-platform-engineer

## ADR-017 · Rules engines: Word Hunt, Cup Pong, Whot! · 2026-11-15

Context: Phase 2 needs the first three games as pure `packages/games` engines (contract in ARCHITECTURE §4, physics in §6). The rules below were not fully set by GAMES.md, so they are decided here. The engines are `wordHuntEngine` (`word-hunt`), `cupPongEngine` (`cup-pong`) and `whotEngine` (`whot`), all exported from `@dyce/games`.
Decision:

- **Whot! (2–6 players, one round, first to play out wins).** Standard 54-card deck (circle and triangle 12 each, cross and square 9, star 7, five Whot 20). Deal 6 cards (2–4 players) or 5 (5–6); the starter card is the first ordinary card (specials found first go to the bottom of the market); the first player comes from the seed. A card matches the top card by shape or number; a Whot (20) goes on anything and names a shape that the next player must follow (a Whot again also works) until a normal card is played. Specials: 1 Hold On (play again), 2 Pick Two, 5 Pick Three, 8 Suspension (next player skipped; with two players you play again), 14 General Market (everyone else picks one, you play again). A Pick Two/Three is answered by playing a card of the same number (the penalty stacks and passes on) or by drawing the whole penalty; a Whot cannot defend. If you cannot or will not play you may draw one card and the turn passes (a draw is always legal, even holding a playable card). When the market runs out the discard pile (except the top card) is reshuffled with the seeded RNG; if nothing can be drawn by anyone for a full round the game ends "blocked". **Last card / Check up:** the play that leaves one card must carry `call: true`, and so must the play that goes out; forgetting costs 2 cards, and a missed "check up" is not a win (the card stays played, you draw 2, play continues). Going out on a special card wins at once (its effect is moot). Placements: first out wins; everyone else is ranked by the points in their hand (card number, Whot = 20), lowest first, ties share a place; a blocked game ranks all players that way and is a draw if the best hands tie. Hands and the market order are hidden; `view()` shows your hand, others' counts, the top card, the requested shape and the pending penalty, and reveals all hands only once the game is over. `whotLegalActions` and `whotAutoAction` are for bots and turn timeouts.
- **Word Hunt (2–8 players, same grid for everyone, async).** 4×4 grid from the seed: letters drawn by English-like weights (no Q), regenerated until it holds at least 25 dictionary words and 3–7 vowels (60 attempts, then the richest). A word is 3+ letters, in the dictionary, traced through neighbouring cells (diagonals too) without reusing one; duplicates count once. Score by length: 3→1, 4→2, 5→4, 6→6, 7→9, 8+→12 (the design's "+400" for a four-letter word is read as a display scale, not a rule; the UI should show `wordHuntWordScore`). Actions are `start` then `submit(words)`, once each. The grid is **hidden from a player until they start** (so it cannot be solved before the clock) and from spectators until the end; the engine cannot read a clock, so **the match service must record when `start` and `submit` arrive and refuse a submit later than `roundMs` (80 000) plus a short grace**. Words that are not valid are dropped and counted in `rejected` (a cheat/lag signal), not scored. A finished player's score is visible to the others at once ("beat 41"), their words only once the viewer has finished too. Highest score wins; equal scores draw. **Dictionary:** a small in-repo list (`wordhunt/words.ts`, about 5 000 words of 3–8 letters, written for Dyce, no third-party licence, no offensive words, a few Nigerian words such as SUYA, JOLLOF, DANFO). It will miss some valid words; `createWordHuntEngine(words, id)` takes any list (e.g. the public-domain ENABLE list loaded on the server), and the state records the dictionary id, so a match keeps the list it started with.
- **Cup Pong (2 players, async).** Each player has 10 cups racked 4-3-2-1 (tip towards the thrower); on your turn you throw 3 balls at the other rack. Input is only `{ aim: -500..500, power: 0..1000 }` (integers). The engine adds a small release wobble from the seeded RNG (aim ±70, power ±26 input units, always two draws per throw) so a perfect replay still misses sometimes, then runs the fixed-step simulation (1/120 s, semi-implicit Euler, only + − × ÷ and sqrt, launch elevation fixed at 52° from literal constants, no trig) against the defender's cups: a ball that crosses a cup's rim plane within 42.5 mm of its axis is in; a clipped rim pops the ball away; cup walls and the table bounce it (3 bounces at most, bounce shots count). State holds integers only (cup positions in mm); the applied input and the outcome are in `last` so the renderer can replay the throw with `simulateCupPongThrow(cups, applied, true)`. **Equal turns:** players[0] throws first each round and, if they clear the rack, players[1] still gets a turn; both clear → fewer balls used wins, equal → draw; after 12 rounds the player with more cups sunk wins, equal → draw. **Re-rack:** once per game, at the start of your own turn, with 2–6 of your own cups left; costs no ball. Measured on the standard rack, a centred, well-judged throw sinks some cup roughly 55–65% of the time, and roughly 40% with three cups left.
  Consequences: (1) Word Hunt needs wall-clock enforcement in the match service (above). (2) Whot is built for a live room: the room should call `whotAutoAction` on a turn timeout and decide what to do when a player leaves (the contract has no forfeit action). (3) The cross-runtime determinism scenario now includes Whot, Word Hunt and Cup Pong games (`pnpm test:determinism`: 16 scenarios, matched in Node only; **Deno and Hermes have not been run**, and the physics only avoids functions known to differ between runtimes). (4) Changing the dictionary, the letter weights, the physics constants or the jitter changes outcomes for the same seed, so a deployed constant change needs a version in the match row. Owner: game-rules-engineer

## ADR-016 · Async matches in a chat (Free) · 2026-11-15

Context: Phase 2 starts the game platform. The first slice is one reference game (`_example`, "Pig") played turn by turn between two friends from a chat, in Free mode, end to end: invite card, accept, moves, result. Pool, counter-offers, Spaces and the real games come on top of this.
Decision:

- **Flow.** `POST /matches` (creator picks the id; it is also the id of the chat card) -> `invited`; the other player `accept`s (the engine's `init` runs with a server-made 62-bit seed, status `active`, state_version 0) or `decline`s / the sender `cancel`s -> `cancelled`; an unanswered invite expires after `match_invite_ttl_hours` (24) and is marked `expired` lazily on the next read or accept. Moves are `POST /matches/:id/moves { expectedVersion, action }`. `GET /matches/:id` and `GET /games` complete the API.
- **The server decides.** A move runs under a row lock (`SELECT ... FOR UPDATE` on the match): member check, action parsed with the engine's zod schema (`invalid_action`), version check, turn check (`not_your_turn`), `validate` (`illegal_move` with the engine's reason), `apply`, append to `match_moves` (seq = version + 1), new state and `current_turn`. When `isTerminal`, placements and results are written to `match_players` from `engine.result` and `settle_match()` finishes the match (for Free it only sets `finished`; Pool will pay out there).
- **Concurrency and retries.** `state_version` is the optimistic check: a move for any other version is `stale_version` (with `currentVersion`), except when it is the same user's same action that produced the move at `expectedVersion + 1`: that is acknowledged as a success and changes nothing, so a lost response can be retried safely (the app resends the same version). Two simultaneous moves leave exactly one. Creating a match is idempotent on its id; accept, decline and cancel are idempotent.
- **No hidden information leaves the server.** `matches.state` holds the full engine state (RNG state, secrets). Every response and every realtime event carries only `engine.view(state, viewer)`, built per player.
- **Realtime.** A new `match` event carries that player's `MatchView`; the hub gets one event per player. The chat card is a `messages` row of kind `game` (id = match id) whose payload is rewritten as the match moves (`updateGameCard`, only forward by `stateVersion`) and published as an ordinary `message` event, so threads and the chat list update without a refetch.
- **Who can play.** Only friends (`match_requires_friends`); the pair must not have blocked each other (checked on create, accept, decline and every move). A conversation that is still a request never carries a game.
- **Dev-only reference game.** The `games` table gets the `_example` row (migration 0012), but the engine registry marks it `devOnly`: the API lists and accepts it only when `NODE_ENV` is not `production`.
- **Not in this slice (BACKLOG).** Pool (`pool_not_available`), counter-offers, turn timers and forfeits (`turn_deadline` stays null), push notifications for "your turn", XP/streak/badge awards, rematch beyond sending a new invite, disputes.
- **Limits.** At most 5 unanswered invites per person per chat (`open_match_invites_per_chat`), 30 creates/min and 120 moves/min per IP.
  Consequences: adding a game means an engine in `packages/games`, an entry in `apps/api/src/matches/engines.ts`, a `games` row and a board in the app (docs/ADDING_A_GAME.md in the app repo). `@dyce/shared` gains the games schemas, the `game` message kind and the `match` event, so the app and the API move together. Owner: game-platform-engineer

## ADR-013 · Block and report · 2026-11-15

Context: SPEC §11 needs blocking (they can't message, invite or see you online) and reporting (reasons plus optional evidence from chat). The data model had `blocks` and `reports` tables and every list, send and lookup already treated a blocked pair as strangers; nothing could create or remove a block or file a report.
Decision:

- **Endpoints:** `GET /blocks`, `POST /blocks`, `DELETE /blocks/:userId`, `POST /reports`. `SafetyService` is a plain class like the others.
- **Blocking is silent and ends the friendship.** The blocked person is told nothing; to them the blocker looks like a user who doesn't exist (existing behaviour in messaging, friends, wallet). The blocker is told "you blocked them" if they try to write. Blocking deletes any friendship or pending request between the two, because that is what people mean by it; unblocking does **not** restore it. The conversation and its history are kept (hidden, not deleted), so it reappears if both become friends again. Idempotent and race-safe (pair lock).
- **Reports** have a fixed set of reasons (`cheat, abuse, scam, spam, name, other`, enforced by a CHECK), an optional note (≤500), optional `conversationId` (must be the reporter's own direct chat with the reported person) and `messageId` (must be in it), and `alsoBlock`. When a conversation is attached the **latest 20 messages are copied into `reports.evidence`** so a moderator sees what the reporter saw even if messages are deleted later. The same reporter, person and reason within 24 hours is one report (double taps and retries); 20 reports per Lagos day (`reports_per_day`). The reported person is never told, and has no way to see that a report exists. A report is kept even if the person is later disabled or blocks the reporter.
- **Not built:** the moderation queue UI and any action on a report (status stays `open`), outcome notifications to the reporter, holding or refunding a Pool stake on a report, and attaching game moves as evidence (there are no matches yet). The app's "A person reviews it" copy promises no deadline.
  Consequences: migration 0011. Messaging's "request" banner and Chat info both offer Report and Block. `@dyce/shared` gains `REPORT_REASONS`, `reportSchema`, `blockSchema`. Owner: trust-safety-compliance

## ADR-012 · Wallet API, money cards and request codes · 2026-11-15

Context: the ledger and its SQL functions existed (ADR-004); Phase 1 needs them reachable from the app: balance, send, request with a QR code, pay a scanned code, history and receipts, with cards in chats.
Decision:

- **Layering.** `WalletService` (a plain class) sits over `LedgerRepo`. Limits, balances, blocks, expiry and idempotency stay in PostgreSQL; the service adds who may pay whom, shapes responses and posts chat cards. Endpoints under `/wallet`: `GET /wallet`, `POST /wallet/topup`, `POST /wallet/send`, `GET /wallet/history`, `GET /wallet/transactions/:id`, `GET|POST /wallet/requests`, `GET /wallet/requests/:code`, `POST .../pay`, `POST .../cancel`.
- **Idempotency keys are scoped to the caller** (`send:<user>:<key>`, `pay:<user>:<key>`). The ledger's key is globally unique, so an unscoped key would let one user replay another's key and read back their transaction id. The app makes one key per confirmation and reuses it on retry.
- **Who can be sent money:** friends, contacts, or someone whose chat both sides have accepted (spec §3). Strangers are paid only by scanning their request code (§4), because the requester shared it on purpose; the resulting chat lands in the requester's Requests, not their Chat.
- **Chat cards.** Message kinds `money_sent` and `money_request` carry a JSON `payload` (amount, note, txn id; or code, status, expiry) and a text `body` ("Sent ₦5,000", "Paid ₦2,000 · suya") so previews and old clients still read sensibly. The card's message id **is** the transaction id (or request id), so posting is idempotent (`ON CONFLICT DO NOTHING`) and a retry re-posts a card lost after the money moved. A card failing never fails the payment (logged). When a request is paid or cancelled, the card's `status` is updated and re-sent live; the app replaces a request card with its newer copy. Cards bypass the stranger message limits: the money movement already passed its own checks.
- **Request codes.** The QR holds only `https://dyce.games/r/<code>`. The Pay sheet always reads the requester, amount and note from `GET /wallet/requests/:code`, never from the QR. An open request past its time reads as `expired` immediately, whether or not a job has marked it. Someone who blocked you (or whom you blocked) makes a code look missing. QR requests last 15 minutes, requests sent to a friend 7 days, at most 10 open at a time.
- **History** is read from the ledger entries of the caller's wallet account, newest first, paged by `(created_at, id)` with a microsecond cursor (the ledger's timestamps are not millisecond-rounded). Receipts only open for someone whose wallet the transaction touched.
  **Update (design pass, 2026-11-15):** the History chips follow the design (`all | pool | transfer | bonus` replace the earlier `sent | received | requests | topups | games`); `GET /wallet` also returns `stats` (won this week, win rate, current streak) and `locked` (stakes held in unfinished Pools), all zero until games are played; `GET /wallet/weekly` returns the last 7 Lagos days of net movement and top-ups (the History bars and the Top-up week grid; the welcome gift is not "net").
  Not done in this step (see BACKLOG): biometric / PIN confirmation, a per-day cap on resolving codes that belong to strangers (only a per-IP throttle for now), the personal "My code" QR and paying a personal code, a scheduled job that marks expired requests and their cards, push for money, disputes, and Pool UI.
  Consequences: `@dyce/shared` gains the wallet schemas and the `Message` type is now a union (`text | money_sent | money_request`), which the app consumes. Owner: wallet-payments-engineer

## ADR-010 · One-to-one messaging, Requests and live delivery · 2026-11-15

Context: Chat must feel instant, keep strangers out of Chat (CLAUDE.md), and not leak who has opened what. This slice is 1:1 text chat; groups, bots, voice, photos, reactions, deletes, game and money cards are later work.
Decision:

- **Model.** One `direct` conversation per pair (`conversations.direct_key` = "low:high", unique), two `conversation_members` rows. A conversation is created by opening it (sends nothing) and appears in lists only once it has a message. Member states: `active`, `request`, `declined`.
- **Requests.** A message to a non-friend creates the conversation with the _recipient_ in `request`: it never shows in their Chat or Chat badge. Before they answer, the sender may send `request_messages_before_accept` (3) messages. The first message is also subject to the recipient's `request_policy` (`nobody`, `fof`) and to `stranger_requests_per_day` (20 new people per Lagos day). Replying, or tapping Accept, makes it active. Decline is **silent**: the member becomes `declined`, the sender sees nothing change and can keep writing up to the same cap, but the recipient gets no live events. While a conversation is a request, opening it sends **no read receipt** (the sender's `peerReadAt` stays null).
- **Friends override.** Once two people are friends, a request or ignored conversation counts as active for both. This is decided when reading (a `CASE` on the friendship row), so nothing needs rewriting when a friend request is accepted.
- **Sending.** The app picks the message id (a UUID), so retrying is safe: the same id returns the stored message and sends nothing; the same id in someone else's conversation is `message_id_taken`. Bodies are trimmed, 1-4000 characters (also a DB CHECK). Created times are server time; history is paged newest-first by the cursor `(created_at, id)`. Sending does **not** mark the thread read (that would hide unread messages the sender hasn't seen).
- **Read state.** `last_read_at` per member, only moves forward. Unread = the other person's messages after it (capped at 99). The Chat tab badge counts unread in active chats, not requests.
- **Realtime.** The `ws` library on the same HTTP server and port, at `/realtime` (no Nest gateway decorators, so it is unit-testable). The first frame is `{type:'auth', token}` (tokens are never in URLs or logs); the socket closes with 4403 when that token expires and the app reconnects with a fresh one, so a revoked session loses live delivery within one access-token lifetime. Limits: 5 sockets per user (oldest dropped), 4 KB frames, 5 s to authenticate, typing 20 per 10 s per socket. Events: `message` (sent to both people, so the sender's other devices update), `read`, `typing`. Typing is checked against the database per signal (member, not blocked, not ignored). Live delivery is best effort: the HTTP API is the source of truth, and on every (re)connect the app refetches its lists and open threads.
- **Single instance.** The hub is in-process. Running more than one API instance needs a shared bus (Redis pub/sub) behind `RealtimeHub.publish` first; until then a message sent through instance A won't reach sockets held by instance B.
- **App.** TanStack Query holds threads (infinite query, newest first) and live events patch that cache. A Zustand **outbox** holds messages being sent or failed (Retry / Delete, with the reason) so they survive navigating away. Typing is a small Zustand store that expires by itself. The thread is an inverted `FlatList` (FlashList later, with the 5,000-message performance pass). On web Enter sends and Shift+Enter is a new line; on phones Return is a new line and the button sends.
- **Deliberately not in this slice** (see BACKLOG): Groups and Bots filters, the "Live now" strip, online dots and "Active now", the "Add friend" choice when accepting a request, a read-receipt opt-out, mute/archive/delete swipes, replies, reactions, delete for me/everyone, voice notes, photos, the Games and money buttons in the composer, and push for new messages. The design's unread count beside the back arrow is omitted.
  Consequences: `ws` is a direct dependency of `apps/api`. `TokenService.verifyAccessWithExpiry` exposes token expiry. Block and report (trust-safety) reuse `blocks`, which messaging already honours (blocked people disappear from lists and look nonexistent). Owner: messaging-engineer

## ADR-009 · Friends list, accept and ignore · 2026-11-15

Context: friend requests existed (ADR-008) but nobody could see, accept or decline them. SPEC says anything from a non-friend goes to Requests, and declining must not become a way to harass or to learn who ignored you.
Decision:

- **Endpoints:** `GET /friends` (A-Z), `GET /friends/requests` (`incoming` and `outgoing`, with mutual-friend counts), `POST /friends/requests/:userId/accept`, `POST /friends/requests/:userId/decline`, `DELETE /friends/requests/:userId` (cancel your own), `DELETE /friends/:userId` (remove). All idempotent; each pair is serialised with an advisory lock.
- **Declined is a real state** (`friendship_status` gains `declined`, plus `responded_at`), not a deleted row. The row is what stops the same person re-sending and re-notifying you.
- **Silent ignore.** The sender is never told. After you decline, their screen still says "Requested" (`pending_out`), they cannot re-send past it, and the daily request cap still applies.
- **Adding back accepts.** If you later add someone whose request you declined, that is treated as accepting their request, so you become friends at once. Their own request is never overridden by a policy check, so accept always works.
- **Remove is quiet and symmetric:** no notification, either side can no longer message as a friend; a later request starts fresh and is subject to `request_policy` again.
- **Mobile:** Friends has All and Requests tabs; Requests shows "Want to be friends" (Accept/Ignore, mutual friends, age of request) above "You asked" (Cancel). The design's swipe-to-remove is replaced by a Remove button with an inline "Keep / Remove" confirm: swipe is not reachable with a screen reader and fails the 44pt target rule when hidden. Until the Profile screen exists, the Chat/Spaces/Wallet top-left avatar opens Friends and carries a count badge for waiting requests.
  Consequences: accepting from the Requests tab is the only place `declined` rows are created; block/report (trust-safety) will reuse the same row and must clear it. Owner: social-discovery-engineer

## ADR-008 · Contact matching and friend requests · 2026-11-14

Context: onboarding must show "who from my contacts is on Dyce" without ever storing the address book (SPEC §4, NDPA 2023), and without turning into a tool for harvesting who is on Dyce.
Decision:

- **Where hashing happens:** the device normalises numbers to E.164 and sends them over TLS in batches of at most 500; the **server** hashes each with the same keyed HMAC used at sign-in (`hashPhone`) and compares with `users.phone_hash`. A plain device-side hash would be trivially reversible (tiny keyspace). Numbers are not logged, validation errors don't echo them, and nothing about unmatched numbers is persisted.
- **What is stored:** only `contact_links(owner, contact_user)` for matches, upserted. `DELETE /contacts` forgets them (data deletion). Links are never removed when a contact disappears from the phone (v1: upsert only).
- **What the server returns:** for each match, the position of the number in the request plus `{ id, username, displayName, relationship }`. Never a phone number or hash. Positions let the app show the **device contact name**, which never leaves the phone. Users with no profile yet, disabled users, yourself, and anyone blocked in either direction are not returned.
- **Abuse:** matching is a membership oracle ("is this number on Dyce?"), so it is capped per user per Lagos day (`contact_lookups_per_day`, default 10,000, counted before matching and rolled back if exceeded) plus a 30/min per-IP throttle. Known limit: an authenticated, phone-verified user can still test up to the cap per day. There is no "hide me from contact matching" setting yet (not in SPEC); worth a product decision.
- **Reading national-format numbers:** contacts like `0803…` are interpreted with the **country of the user's own verified number** (stored in the session as an ISO code only), falling back to the device region. Using the device region alone silently dropped a Nigerian user's contacts on a phone set to US English (found in testing).
- **Friend requests (minimal):** `POST /friends/requests` creates a pending request, or accepts one the other person already sent (reciprocal), idempotently and race-free (advisory lock per pair). Rules: someone who blocked you looks nonexistent; you can't add someone you blocked; the target's `request_policy` applies to _new_ requests (`nobody` refuses, `fof` needs a mutual friend or a contact link; accepting is always allowed); 50 new requests per day. Listing, accepting, declining and removing friends belong to the social/discovery work.
- **Find by username:** `GET /users/by-username/:username` is exact match only (no prefix search), so it can't be used to browse users.
- **Denied path:** if contacts are refused (or the platform has no address book), the screen offers "Allow in Settings" and "Find by username" and lets the user continue.
  Consequences: contact matching depends on `PHONE_HASH_SALT` staying stable (see ADR-007). `expo-contacts` in SDK 58 moved its stable API to `expo-contacts/legacy`; we use that import. Owner: auth-onboarding-engineer

## ADR-007 · Phone OTP auth, sessions and the age gate · 2026-11-14

Context: Phase 1 needs sign-in with a phone number only (no passwords, no social login in v1), safe against enumeration, SMS pumping and token theft, and privacy-preserving (NDPA 2023: no raw phone numbers stored or logged).
Decision:

- **OTP:** 6 digits from the OS CSPRNG, 5 minute TTL, stored only as `HMAC(secret, challengeId:code)`; compared in constant time; one use; max 5 wrong tries then locked; only the newest code is valid. Requesting a code answers identically whether or not the number has an account.
- **Rate limits:** per phone 30 s resend cooldown, 3 per 10 minutes, 10 per day (database-backed, serialised with an advisory lock so concurrent requests can't slip past); per IP via `@nestjs/throttler` (OTP routes 10/min, refresh 30/min, everything else 120/min). A failed SMS send deletes the challenge so our provider's outage doesn't burn the user's limit.
- **Phone numbers:** normalised to E.164 with libphonenumber-js (same function in app and server), stored only as `HMAC-SHA256(PHONE_HASH_SALT, "phone:"+e164)` in `users.phone_hash`. The same secret keys OTP hashes under a different prefix. Rotating it breaks contact matching.
- **Sessions:** access token = HS256 JWT (`jose`), 15 minutes, claims `sub` and `sid` (session family); refresh token = 256-bit opaque, 30 days, only its SHA-256 stored, **rotated on every use**. Presenting an already-rotated token revokes the whole family (theft signal). We do not check revocation on every request, so a revoked session's access token can live up to 15 minutes. The app's API client therefore shares **one** in-flight refresh across concurrent 401s, since replaying a refresh token would sign the user out.
- **SMS:** `+234` goes to Termii first and falls back to Twilio; everything else uses Twilio. **Both adapters are unit-tested against recorded request shapes only; neither has been exercised against the live service**, and Termii's base URL and channel (`dnd`) must be confirmed against the account at integration time. `SMS_DRIVER=console` (dev) prints the code with the number masked. `OTP_TEST_CODE` (fixed code, no SMS) exists for Maestro and local work and the API **refuses to start** with it, or with the console driver, when `NODE_ENV=production`.
- **Android OTP autofill:** iOS uses `textContentType="oneTimeCode"`; Android relies on keyboard/autofill suggestions via `autoComplete="sms-otp"`. A native SMS Retriever / User Consent module is deferred (needs a dev build to evaluate); manual entry always works.
- **Username:** `a-z 0-9 . _`, 3-20, no leading/trailing dot, no `..`, case-insensitively unique; reserved names (`admin`, `dyce`, `support`, ...) are blocked in the schema **and** by a database trigger.
- **Age gate:** only a birth year is collected, so 19+ is treated as adult (an 18-year gap can't be told from 17 or 18). The year can be set **once** (API and a database trigger), so a minor cannot retry years until one passes. Pool staking requires `is_adult` in the ledger function itself. If the product later wants exact 18, collect a full date of birth.
- **Onboarding progress** is derived from data (profile exists, welcome grant really in the ledger) plus client-reported steps (`contacts`, `avatar`, `notifications`) so a restarted app resumes at the earliest unfinished step.
  Consequences: we own OTP, sessions and abuse limits now (Supabase Auth did this before ADR-004). Apple/Google sign-in shown in the original welcome design is out of scope (SPEC §4 is phone-only). Contacts matching, the avatar builder and push registration are separate work; their onboarding screens are placeholders that can be skipped. Owner: auth-onboarding-engineer

## ADR-005 · Explicit `.ts` extensions in shared packages · 2026-11-14

Context: `packages/games` must run unchanged in Node (NestJS, Colyseus, determinism script), Jest and Hermes. Decision: relative imports in `packages/games` and `packages/shared` end in `.ts`; `allowImportingTsExtensions` is on. Node 22 strips types natively, so `node script.ts` runs the engines with no build step. Consequences: no bundler-only resolution tricks in these packages. Owner: platform-architect

## ADR-004 · NestJS + plain PostgreSQL replace Supabase · 2026-11-14

Context: the product owner chose NestJS for the backend and plain Postgres with SQL migrations; NestJS owns the API. The kit assumed Supabase (Postgres, Auth, Realtime, Edge Functions) plus Colyseus.
Decision: `apps/api` is a NestJS app (REST + WebSocket gateway). PostgreSQL 16+ (tests run on 17) accessed with `pg` (no ORM, so the ledger functions stay explicit SQL). Migrations are ordered `.sql` files in `apps/api/db/migrations` applied by a small runner. Auth is ours: phone OTP (Termii/Twilio adapter), short-lived JWT + rotating refresh token. Realtime chat is a NestJS WebSocket gateway. Colyseus stays for live rooms and verifies our JWT. DB tests are Jest integration tests against a real Postgres (docker compose) instead of pgTAP. File storage (avatar renders, voice notes) is S3-compatible behind a `StorageService` interface; the provider is a [HUMAN] pick later.
Consequences: we now own OTP, sessions, rate limiting and websocket scaling that Supabase provided; all "RLS" rules from ARCHITECTURE §3 become service-layer authorization plus SQL constraints. Money, ledger and fairness rules are unchanged. Hosting: any Node + Postgres host (Fly.io + managed Postgres is the default). Owner: platform-architect, supabase-backend-engineer (now owns apps/api)
